# Spiral Knights technical architecture, open-source components, and community reverse-engineering (state as of 2026-10-12)

Scope note for the writer: Spiral Knights is a closed-source Java game whose *engine and framework layers* (Clyde, Narya, Nenya, Vilya, Getdown, samskivert/ooo-util, Depot) are open source, while the game-specific layer ("projectx": `code/projectx-pcode.jar` + `code/projectx-config.jar`/`config.jar` + `rsrc/`) is proprietary and obfuscated. The single most important 2025–2026 development is that Grey Havens has been actively modernizing both the open-source engine repos (Clyde master now targets Java 25 and LWJGL 3.4.3, last commit 2026-10-07) and the live client (Java upgrade shipped 2026-02-18; Apple-silicon support shipped 2026-05-05). Anything describing "LWJGL 2 / Java 6–8" is pre-2026 and should be flagged as such.

## Key Question 1: Engine — what Clyde provides, license, maintenance, Java/LWJGL targets, natives, AWT/Swing

### Takeaway
Clyde is Three Rings'/Grey Havens' BSD-licensed Java 3D game library: a fixed-function-plus-GLSL OpenGL renderer, scene graph/compositor, material/model/animation/particle systems, a reflective config + versioned binary/XML export system, the "Tudey" 2.5D scene/physics/server-logic engine, an expression system, and Swing-based editors. As of October 2026 it is actively maintained by a Grey Havens engineer, targets Java 25 and LWJGL 3.4.3 (GLFW + OpenAL + lwjgl3-awt), and still leans heavily on the OpenGL compatibility profile (fixed-function matrix stack, lighting, fog, texgen, client arrays) alongside GL20 shaders, GL15 VBOs, GL30 FBOs/VAOs.

**Binary export format (Clyde `export` package) — relevant to .dat assets**
- `BinaryExporter`: preamble `MAGIC_NUMBER = 0xFACEAF0E` (int), `VERSION = 0x1002` (short), then a short flag word with `COMPRESSED_FORMAT_FLAG = 0x1000` if compressed. Default constructor sets `compress = true`; everything after the preamble is wrapped in a `DeflaterOutputStream` (not GZIP). Objects are preceded by varint object ids (identity-tracked, strings interned); classes are written as varint class id + class name via `Streamer.writeUTF` + one flag byte (`FINAL_CLASS_FLAG`, `INNER_CLASS_FLAG`, `COLLECTION_CLASS_FLAG`, `MAP_CLASS_FLAG`, `MULTI_FLAG`); `BOOTSTRAP_CLASSES` seed ids 1–8 with primitive types; `Exportable` objects write fields as varint count + per-class field-id table (new fields write id + name + class); `Streamer.getStreamer()` handles directly-streamable types; `Multimap` unsupported ("TODO"). — [BinaryExporter.java](https://raw.githubusercontent.com/threerings/clyde/master/core/src/main/java/com/threerings/export/BinaryExporter.java)

### Inferences
- Because Clyde core now depends on `lwjgl-glfw` *and* `org.lwjglx:lwjgl3-awt`, and still ships both `GlDisplayApp` and `GlCanvasApp`/`GlCanvas`, the runtime supports two windowing paths: a GLFW window and an AWT-canvas-hosted GL context. The editors (`GlCanvasTool`, `editor` package) are Swing-based. Whether the *live game client* uses the GLFW or the AWT path is not public (see Gaps).
- The Android port (SKapsule, below) required a "headless AWT bridge" (caciocavallo) to boot the game, which strongly implies the client still needs `java.awt` classes at runtime (fonts/images/`Toolkit`), not just in the editors.
- The renderer is a compatibility-profile design: fixed-function matrix stack, lighting, fog, texgen, client arrays and texture environments coexist with GLSL programs. A browser port via WebGL/WebGPU would need to emulate fixed-function state (or run through a GL-compat translation layer like gl4es — which is exactly what the Android port does).
- `proguard-annotations` as a Clyde dependency implies the game build is ProGuard-processed (consistent with the obfuscation evidence in KQ6).
- Clyde's `delta` package ("delta encoding on Narya streaming") and `tudey.dobj` suggest Tudey transmits scene deltas via Presents distributed objects; the Tudey server classes (`TudeySceneManager`, `ClientLiaison`, `logic/`) provide the generic authoritative-server movement/scene logic the game builds on.

- No public document states which Clyde app base class (`GlDisplayApp` vs `GlCanvasApp`) the Spiral Knights client extends, nor the exact GL version/profile it requests.
- Clyde's Javadoc site and the `tests/` examples referenced in the README were not fetched; there is no in-repo format or Tudey documentation (`docs/` has only a stylesheet).

## Key Question 2: Networking/server framework — Narya/Presents, Nenya, Vilya, samskivert, Depot; wire protocol; ports; auth; UDP

### Takeaway
The client talks to the server with Narya's "Presents" protocol: a blocking TCP `SocketChannel` carrying 4-byte big-endian length-prefixed frames of `com.threerings.io.ObjectOutputStream`-serialized `UpstreamMessage`/`DownstreamMessage` objects, an optional RSA-public-key → `SecureRequest`/`SecureResponse` → `AESAuthRequest` login handshake, then a `BootstrapNotification`, followed by distributed-object subscription/event traffic; an optional unreliable UDP datagram channel is negotiated by pinging `datagram_ports` and authenticated with an MD5 of payload + per-session secret. Spiral Knights specifically uses TCP 47624 and UDP 47625 (per the Thetya private-server README's instructions for editing `deployment.properties` in `config.jar`).

**Presents architecture (docs/presents/overview.html)**
- Client/server star topology: "All information transfer takes place through the server." Distributed objects live on the server; clients subscribe and hold proxies kept current by events; setters generate events that the server validates and rebroadcasts; public fields are attributes, non-public/`transient` not transmitted; generated setters/constants; `DObjectManager.createObject`, `subscribeToObject`, `SafeSubscriber`; `AttributeChangeListener`, `ElementUpdateListener`, `DSet`/`SetListener`; invocation-services and Ant-task sections marked "TBD"; nothing on wire format or datagrams. — [overview.html](https://raw.githubusercontent.com/threerings/narya/master/docs/presents/overview.html)

**Wire protocol as implemented (`BlockingCommunicator`)**
- Transport: blocking `java.nio.channels.SocketChannel` with `setKeepAlive(true)`; connects to `_client.getPorts()[0]` at `_client.getHostname()` ("does no cycling" of TCP ports in this implementation). — [BlockingCommunicator.java](https://raw.githubusercontent.com/threerings/narya/master/core/src/main/java/com/threerings/presents/client/BlockingCommunicator.java)
- Framing/serialization: `FramingOutputStream`/`FramedInputStream`; `com.threerings.io.ObjectOutputStream` + a `ClientObjectInputStream`; outbound `_oout.writeObject(msg)` → `frameAndReturnBuffer()` → `channel.write`; writes over 4096 bytes log "Whoa, writin' a big one." — [BlockingCommunicator.java](https://raw.githubusercontent.com/threerings/narya/master/core/src/main/java/com/threerings/presents/client/BlockingCommunicator.java)
- Frame format: 4-byte length prefix (`HEADER_PAD = new byte[4]`), **length includes the 4-byte prefix**, big-endian; no max-size check in this class. — [FramingOutputStream.java](https://raw.githubusercontent.com/threerings/narya/master/core/src/main/java/com/threerings/io/FramingOutputStream.java)
- Handshake: (1) connect; (2) if `_client.getPublicKey()` is set, send `SecureRequest(new PublicKeyCredentials(key), version)`, await `SecureResponse`, then send `AESAuthRequest.createAuthRequest(creds, version, bootGroups, requireSecureAuth, pubKeyCreds, secureResponse)` and call `_client.setSecret(areq.getSecret())`; otherwise send `AESAuthRequest.createAuthRequest(creds, version, bootGroups, requireSecureAuth)`; (3) `gotAuthResponse` → `LogonException(data.code)` unless `AuthResponseData.SUCCESS`; (4) `logonSucceeded` creates `ClientDObjectMgr`, then waits for the bootstrap notification; `gotBootstrap()` starts the `DatagramReader` if `getDatagramPorts().length > 0`. — [BlockingCommunicator.java](https://raw.githubusercontent.com/threerings/narya/master/core/src/main/java/com/threerings/presents/client/BlockingCommunicator.java); [Communicator.java](https://raw.githubusercontent.com/threerings/narya/master/core/src/main/java/com/threerings/presents/client/Communicator.java)
- UDP: non-blocking `DatagramChannel` with `setTrafficClass(0x10)`; tries each datagram port with `DATAGRAM_ATTEMPTS_PER_PORT = 10` pings, `DATAGRAM_RESPONSE_WAIT = 1000 ms`; on success posts `TransmitDatagramsRequest` and starts a `DatagramWriter`. Datagram layout: 4-byte connection id, 8-byte auth slot, then `DatagramSequencer` payload from offset 12; auth = first 8 bytes of MD5(payload-from-offset-12 ‖ `getDatagramSecret()` UTF-8) written at offset 4; oversize (> `Client.MAX_DATAGRAM_SIZE`) dropped; out-of-order datagrams discarded by `DatagramSequencer.readDatagram()`. Only messages with unreliable `Transport` go via UDP. Reliable sends sleep 2 ms while `Throttle.throttleOp()` is true; datagram writer drops when throttled. `PingRequest` is used only during datagram setup in this class. No automatic reconnect. — [BlockingCommunicator.java](https://raw.githubusercontent.com/threerings/narya/master/core/src/main/java/com/threerings/presents/client/BlockingCommunicator.java)

**Spiral Knights-specific endpoints and config keys (from the Thetya private-server README)**
- To point the real client at a private server: edit `deployment.properties` inside the client's `config.jar`, setting `server_host`, `server_ports` = **47624**, `datagram_ports` = **47625**, and `key.public` to the server's RSA public key; the server reads its private key from `key.private` in `rsrc/server.properties` and binds via `hostname.bind`. Keypair generated with `com.github.thetya.server.tools.RsaKeypairGenerator`. Accounts are created with `siteId` 204, "the ID for Spiral Knights." — [excal69/thetya](https://github.com/excal69/thetya)
- A community packet sniffer docstring also names **47624** as the Spiral Knights game-server port and captures `tcp portrange 47620-47640` (TCP only; it does not decode frames). — [live_monitor.py](https://raw.githubusercontent.com/xiao2718/Spiral-Knights-Traffic-Monitor/main/live_monitor.py)
- Thetya's `ThetyaServer` extends `com.threerings.tudey.server.TudeyServer`, uses `com.threerings.nio.conman.ServerSocketChannelAcceptor` (SO_REUSEADDR), `com.threerings.presents.server.{ClientResolver, PresentsSession, SessionFactory}`, `com.threerings.presents.net.AuthRequest`, `com.threerings.admin.server.ConfigRegistry`, `com.threerings.config.dist.server.DConfigManager`, Guice injection, `com.samskivert.util.AuditLogger`; sets `com.threerings.io.enumPolicy=ORDINAL`; reads `ServerConfig.getListenPorts()/getDatagramPorts()/getBindHostname()/getDatagramHostname()/getPrivateKey()`. — [ThetyaServer.java](https://raw.githubusercontent.com/excal69/thetya/main/src/com/github/thetya/server/ThetyaServer.java)

### Inferences
- The `key.public` in `deployment.properties` + `PublicKeyCredentials`/`SecureRequest`/`AESAuthRequest` path means the live SK login is the Narya "secure auth" flow: client encrypts an AES session secret to the server's RSA public key, and that secret also keys UDP datagram authentication. The exact credential class the SK client uses (`UsernamePasswordCreds` vs a Steam/ticket subclass) is not public.
- The 4-byte-length framing over plain TCP (no TLS) means a browser port would need a WebSocket→TCP relay (or server-side WebSocket support) that re-frames messages; the Java-reflection-based `Streamable` serialization (class names on the wire, `ClassMapping`) means a JS client must reimplement `com.threerings.io.ObjectInputStream` semantics — including `enumPolicy=ORDINAL` as set by Thetya's server (suggesting the SK client also expects ordinal enums).
- The datagram channel is optional by design (`getTransmitDatagrams()` defaults false; UDP only if ports respond), so a browser client could function TCP-only, at the cost of whatever SK sends as unreliable `Transport`.

### Gaps
- `com.threerings.io.ObjectOutputStream`'s exact byte format (class-code tables, how `Streamable` fields/`ClassMapping` are encoded, string encoding) was not read; only the frame format and handshake were sourced.
- `AESAuthRequest`/`SecureResponse` internals (cipher mode, key sizes, how the secret is derived) were not read.
- No official Grey Havens/Three Rings document of the SK-specific message set (`com.threerings.projectx.*` invocation services, Tudey delta events) exists publicly; the `docs/presents/design.txt` and `notes.txt` were not fetched.
- Whether the live servers also use Narya's "peer" (`peer` dir in Thetya) and "bureau" systems is not documented publicly.

## Key Question 3: Launcher/distribution — Getdown, install layout, bundled JRE, Steam vs standalone

### Takeaway
Spiral Knights is deployed with Getdown (Three Rings' BSD-licensed Java Web Start replacement): a `getdown.txt` manifest + `digest.txt` drives download/verification of `code/*.jar` and `rsrc/**` from an `appbase`, with a bundled JVM in `java_vm/` and binary `patch*.dat` deltas. The classic Windows install contained `getdown-pro.jar`, `launcher.exe`, `code/{projectx-pcode.jar, projectx-config.jar, config.jar, lwjgl.jar, lwjgl_util.jar, jinput.jar, jshortcut.jar, jutils.jar, commons-*.jar, getdown-pro-new.jar}`, `rsrc/`, and a Java 6/7/8-era `java_vm/`; since February 2026 the client "bundles its own runtime" at a newer Java version. Linux has no standalone download anymore (Steam only), while the Windows/Mac standalone installers still exist.

## Key Question 4: Assets — rsrc/ tree, .dat format, textures, audio, config bundles, UI, and tooling

### Takeaway
Game data lives in `rsrc/` as Clyde `export` binary files (`.dat`, magic `0xFACEAF0E`, Deflate-compressed by default, round-trippable to XML with Clyde's `BinaryToXMLConverter`/`xml2dat`), organized as config catalogs (`rsrc/config/*.dat`: `item.dat`, `actor.dat`, `accessory.dat`, `attack.dat`, `shader.dat`, `texture.dat`, `wall.dat`, `level_table.dat`, etc.), model files (`model.dat` under paths like `rsrc/character/npc/...`), material/texture refs, and server-downloaded Tudey scenes cached in `scenes/`; audio is OGG/MP3/WAV via Nenya's OpenAL layer. Community tooling is mature: SpiralSpy (2011, Clyde ModelViewer wrapper) → SpiralView (Clyde editors rebuilt against `projectx-pcode.jar`, now folded into Knight Launcher), ThreeRingsSharp (C#/IKVM Clyde→glTF ripper), Kozmadeus/Bootshuze (OBJ/DAE → Clyde XML model importer), Cogmaster (config lookup API/bot), sk-stat-extractor (config .dat → XML).

### Cited Findings

**Formats**

### Inferences
- `.dat` is not a single format: config catalogs, models, materials, animations, and scenes are all Clyde `Exportable` object graphs serialized by `BinaryExporter`, so a JS reader needs (a) an inflate step, (b) the varint/class-table/field-table decoder, and (c) the *schema* of each `com.threerings.projectx.*` and `com.threerings.opengl.*.config` class to interpret fields — the Clyde classes are open source, the projectx ones are obfuscated/proprietary. The "scripts" remark in old forums most likely refers to `ScriptedConfig`-type model/action configs rather than a text format.
- Textures appear to be ordinary PNGs referenced by material configs (`texture.dat`), and GUI images are PNG; no evidence of DDS/compressed texture formats (and `Renderer.java` has no S3TC path).
- Because every community tool that reads SK assets (SpiralSpy, SpiralView, Cogmaster, sk-stat-extractor, Knight Launcher) requires `projectx-pcode.jar` on the classpath, the obfuscated game classes are needed to deserialize game-specific config objects; a browser port would need either those class schemas or a server-side converter to a neutral format.

### Gaps
- No public, complete inventory of the current `rsrc/` tree (directory names, counts, extensions, bundle jars) exists in any fetched source; the uninstaller listing is partial and old.
- The UI definition format (Clyde `opengl.gui` is JME-BUI-derived; whether SK UIs are `.dat` configs or code) is undocumented.
- The `.skal` Crucible file format and whether the Crucible editor is the Tudey scene editor re-skinned are undocumented.
- Texture formats were not directly confirmed (inferred PNG).

## Key Question 5: Community reverse engineering, private servers, offline play, protocol docs

### Takeaway
There is exactly one public Spiral Knights server reimplementation — "Thetya" (GitHub `excal69/thetya`, plus a 16 MB "early source" zip on the Internet Archive from Oct 2023) — built on the open-source Narya/Clyde Tudey server stack with Guice, MySQL/MariaDB/Postgres, and a broad manager set (dungeon, pvp, exchange, guild, town, scene, etc.), but with no stated status, license, or evidence it runs today. Everything else is client-side: launchers (Knight Launcher; Android ports KnightLauncher-Android → SKapsule), a read-only headless Presents client, a naive TCP sniffer, mod toolchains, and scene archiving. No published protocol documentation beyond Narya's own source exists, and Knight Launcher explicitly refuses to enable third-party-server support while official servers are online.

### Inferences

## Key Question 6: Client internals — obfuscation, jar contents, Java version, platforms, GL requirements

### Takeaway
The game code is `code/projectx-pcode.jar` (obfuscated and *re-obfuscated on every update*, per modders) plus `projectx-config.jar`/`config.jar` (holding `deployment.properties` with server host/ports/public key); game-specific code lives under `com.threerings.projectx.*` on top of Clyde/Narya.
