# Java/LWJGL game to browser: toolchains and case studies (state as of 12 Oct 2026)

Scope note for the report writer: this file covers the compiler/runtime options for getting JVM bytecode (specifically a Java 3D game built on LWJGL 2.x + Three Rings' Clyde engine, i.e. Spiral Knights) running in a web browser, plus the real-world precedents. Profile kept in mind throughout: single-threaded render loop, background threads for networking and asset loading, LWJGL 2 (`Display`, `GL11`..`GL20`/`GL30`, `AL10`, `Keyboard`, `Mouse`), GLSL shaders, raw TCP to a game server.

## KQ1. TeaVM: version/status 2025-2026, JS vs Wasm backends, limitations, performance, how big projects cope

### Takeaway
TeaVM is actively maintained (0.16.0 released 2 Oct 2026, roughly two feature releases per year) and is the only free bytecode-to-web compiler with a production-grade JS backend plus a near-parity Wasm GC backend; the legacy linear-memory Wasm and WASI backends were deleted in 0.14.0. Its constraints are structural: green threads via CPS transformation (no real parallelism), whitelist-only reflection, no class loaders/JNI/AWT, and a class library that is thin in `java.net`, `java.util.concurrent`, `java.nio.channels` and `java.security`.

**Compilation model and restrictions**
- TeaVM is an ahead-of-time compiler from Java *bytecode* (not source) to JavaScript, "similar to GWT" but able to consume output of javac, kotlinc or scalac; it "restricts reflection, resources, class loaders, and JNI because they can't be implemented efficiently in JavaScript"; threads are emulated as green threads via continuation-passing-style transformation; it emits source maps and has an IDEA debugger plugin; it claims dead-code elimination yields "very small JavaScript" and that devirtualization makes code faster (no numbers). — [TeaVM overview](https://teavm.org/docs/intro/overview.html)
- For "tightly coupled Swing applications" the TeaVM docs say you "should probably look elsewhere" and recommend CheerpJ. — [TeaVM overview](https://teavm.org/docs/intro/overview.html)

**Threading model (coroutines / green threads)**
- JavaScript has no threads; WebWorkers are process-like with no shared sync primitives; TeaVM therefore "uses coroutines to emulate the `Thread` class and a few simple synchronization primitives"; creating and starting a `Thread` works as in Java; `synchronized`, `Object.wait`, `Object.notify` work. — [TeaVM coroutines doc](https://www.teavm.org/docs/runtime/coroutines.html)
- The `@Async` mechanism: declare a `native` method marked `@Async`, plus a sibling `void` method taking the same params plus `AsyncCallback<T>`; call `callback.complete(...)`/`error(...)` from the JS callback; the doc's example makes `XMLHttpRequest` look synchronous. This is how blocking I/O (sockets, fetch) is modelled. — [TeaVM coroutines doc](https://www.teavm.org/docs/runtime/coroutines.html)
- Restriction: a coroutine cannot be passed to a JS function that expects an immediate result (e.g. `Array.prototype.map`); if a lambda handed to such a JS API becomes a coroutine, TeaVM throws. — [TeaVM coroutines doc](https://www.teavm.org/docs/runtime/coroutines.html)
- 0.16.0 added a "clear Java exception when a suspension point is reached outside of a thread context" on Wasm GC (i.e. calling suspending code from a raw JS callback such as `requestAnimationFrame` is an error). — [TeaVM 0.16.0](https://github.com/konsoletyper/teavm/releases/tag/0.16.0)
- `Thread.join` could hang until fixed in 0.14.1. — [TeaVM releases](https://github.com/konsoletyper/teavm/releases)

**Class library coverage (official JCL report, "partial % / full %")**
- `java.nio` 92/35; `java.nio.channels` 15/15; `java.net` 18/12; `java.io` 64/46; `java.util.concurrent` 20/14; `java.util.concurrent.atomic` -/18; `java.util.zip` 80/28; `java.lang.reflect` 51/21; `java.lang` 76/50; `java.security` 13/8; `java.util.logging` -/0; `java.util.regex` -/25; `java.util.stream` -/20; `java.lang.invoke` -/15; `java.util.function` 100/100. **`java.awt`, `java.awt.image`, `javax.imageio`, `javax.sound` are not in the report at all**, i.e. absent. — [TeaVM JCL report](https://teavm.org/jcl-report/recent/jcl.html)

**Reflection in practice**
- gdx-teavm docs: apps configure reflection via TeaVM's `ReflectionPolicy`/`SimpleReflectionPolicy`; policies grant member access only, and classes must additionally be kept via `preservedClasses`; no automatic package scanning. Known limitation with TeaVM `0.16.0-dev-6`: a preserved, policy-approved class referenced only by runtime name can still fail `ClassReflection.forName`. — [gdx-teavm usage.md](https://github.com/xpenatan/gdx-teavm/blob/master/docs/usage.md)
- jMonkeyEngine port: any reflection beyond stock jME usage had to be whitelisted in `TeaReflectionSupplier.java` and classes listed in `classesToPreserve` in `build.gradle` so the optimizer keeps them. — [jME TeaVM port thread](https://hub.jmonkeyengine.org/t/porting-jmonkeyengine-to-the-browser-with-webgl2-and-teavm-sourcecode-released/47020)

**Wasm GC backend specifics**
- Loader: include `<name>.wasm-runtime.js` (registers `TeaVM.wasmGC`), then `TeaVM.wasmGC.load(src, options)`; options include `memory: { minSize, maxSize (default 2 GiB), shared, external, onResize }`; linear memory is used for direct NIO buffers and for moving data to/from JS typed arrays; shared memory requires COOP/COEP headers; Node.js supported. — [Wasm GC loader API](https://www.teavm.org/docs/wasm-gc-backend/loader.html)
- Emscripten integration: compile C libs with `MODULARIZE`, `RELOCATABLE`, `EXPORT_ES6=1`, `ALLOW_MEMORY_GROWTH=1`, `MALLOC=none`, `--no-entry`, pass via `emscriptenModules`; C stack default 2 MiB. — [Wasm GC loader API](https://www.teavm.org/docs/wasm-gc-backend/loader.html)
- Debugging on Wasm GC: `stackDeobfuscator` option maps Wasm addresses in stack traces back to Java class/method/file/line (recommended off in production); Java exceptions surface as JS `Error` with the Java message. — [Wasm GC loader API](https://www.teavm.org/docs/wasm-gc-backend/loader.html)
- IntelliJ's TeaVM debugger "works with JavaScript only, not Wasm"; the dev server supplies source maps, Java sources and debug metadata to browser devtools. — [gdx-teavm usage.md](https://github.com/xpenatan/gdx-teavm/blob/master/docs/usage.md)
- Eaglercraft's measurement of TeaVM Wasm GC vs TeaVM JS on the same game: "around 50% more FPS and TPS in some cases" (README excerpt quoted by the search engine; see Eaglercraft section for the source caveat). — [EaglercraftX README mirror (excerpt)](https://purnhab68-gitea.hf.space/eymenwsmc/Eaglercraft-1.7.10/raw/branch/main/EAGLERCRAFTX_README.md)

**Tooling**
- Gradle plugin `org.teavm` exists (it is what the Renovate PR bumps); Maven plugin `compile` goal honours toolchains since 0.16.0; IDEA plugin; dev server with hot update. — [edward3h/kv2 PR #617](https://github.com/edward3h/kv2/pull/617); [TeaVM 0.16.0](https://github.com/konsoletyper/teavm/releases/tag/0.16.0)
- TeaVM is Apache-2.0; a maintainer notes "many independent game developers using TeaVM libGDX backend". — [search excerpt citing TeaVM README/sponsors page](https://sponsors.ecosyste.ms/accounts/konsoletyper)

### Inferences
- For the Spiral Knights profile, TeaVM's coroutine model is adequate: a background "network thread" that blocks in a `read()` becomes a coroutine suspended on an `@Async`-wrapped WebSocket `onmessage`; an asset-loading thread blocks on `fetch`. What does *not* carry over is anything that assumes true parallelism (e.g. spinning on a volatile, or expecting the render loop to progress while a loader thread does CPU-bound decoding). CPU-bound work on a "background" thread will stall rendering unless it yields (sleep/wait) or is moved to a Web Worker with message passing.
- Because the render loop is typically driven from `requestAnimationFrame` (a raw JS callback), any code reachable from the frame callback that can suspend (e.g. a `synchronized` block that contends, `Thread.sleep`, or an `@Async` call) will now throw on Wasm GC (0.16.0 behaviour) or misbehave on JS; the game loop must be restructured so the frame callback never suspends (Eaglercraft and gdx-teavm both structure it this way).
- `java.nio.channels` at 15% and `java.net` at 12% full coverage means Clyde/Narya's `SocketChannel`-based networking will not compile as-is; it has to be replaced at the transport layer with a WebSocket client (TeaVM ships WebSocket JSO bindings, per the jME thread).
- `java.util.concurrent` at 14% full and `java.util.concurrent.atomic` at 18% full means executor/queue-heavy code needs auditing; expect to substitute simple implementations.
- No `java.awt`/`javax.imageio` at all: any image decoding, font rasterisation (`java.awt.Font`) or `BufferedImage` use must be rerouted to browser APIs (`<canvas>`, `ImageBitmap`, `OffscreenCanvas`) via JSO. This is the same situation as GWT.
- Serialization (`ObjectInputStream`) and dynamic class loading are effectively unavailable (class loaders restricted; whole-program AOT); any format that relies on Java serialization or on `Class.forName` with runtime-computed names needs a reflection policy entry per class or a code-generated registry.

### Gaps
- I could not fetch the dedicated "Wasm GC backend" doc page (it returned only navigation), so the official list of required browser versions / Wasm proposals (GC, exception handling, JS string builtins) for TeaVM's Wasm GC output is not confirmed from TeaVM's own docs. Kotlin's documented WasmGC browser floor (Chrome 119+, Firefox 120+, Safari 18.2+) is the best proxy; see KQ4.
- No official TeaVM benchmark comparing Wasm GC vs JS backends was found; the only number is Eaglercraft's ~50% figure.
- No official statement on maximum practical project size / compile time for very large bytecode inputs; the only anecdotes are Eaglercraft (full Minecraft 1.8 client) and libGDX games.

## KQ2. Eaglercraft (EaglercraftX 1.8, Eaglercraft 1.5.2 and later): architecture, networking, threading, storage, assets, WASM-GC/WebGPU, legal history

### Takeaway
Eaglercraft is the proof that a full LWJGL-2-era Java 3D game can run on TeaVM: lax1dude hand-rewrote LWJGL (about a month of work), wrote an "OpenGL 1.3 emulator built on top of WebGL 2.0" (with a WebGL 1.0 fallback that runs back to Chrome 38), proxies Minecraft's TCP protocol over WebSockets through a server-side plugin (EaglerXBungee, now EaglerXServer for Spigot/Bungee/Velocity), uses WebRTC with WebSocket signalling relays for "Shared Worlds", ships assets as a single `assets.epk` bundle, and since 2024-2025 has an experimental WASM-GC build on a TeaVM fork that is ~50% faster but needs JSPI. Mojang/Microsoft have pursued it with DMCA notices continuously since Nov 2022 and the GitHub mirrors are 451-blocked today; development continues on a self-hosted Gitea.

### Cited Findings

**What it is / history**
- Eaglercraft: browser ports of Minecraft Java Edition compiled to JavaScript with TeaVM plus an OpenGL emulator; development began early 2020, first release based on Minecraft 1.5.2 (multiplayer only), then a Beta 1.3 port that added singleplayer; EaglercraftX (port of 1.8.8) was developed in secret from May 2022 for about seven months; "stable release is EaglercraftX u45, dated December 14, 2024"; PeytonPlayz595 separately ported Indev/Infdev/Alpha 1.2.5/Beta 1.7.3/Release 1.2.5; a community 1.12.2 port exists. — [HandWiki: Eaglercraft](https://handwiki.org/wiki/Software:Eaglercraft)
- "Minecraft depends on LWJGL, which TeaVM cannot use. Lax1dude rewrote that dependency by hand, a task that took about a month." An OpenGL emulator by lax1dude enables gameplay in browsers; the project was designed to run from a single HTML file; EaglercraftX is distributed as *patch files* against decompiled Minecraft (like a mod), not as game source. — [HandWiki: Eaglercraft](https://handwiki.org/wiki/Software:Eaglercraft)
- Early EaglercraftX README (mirror): the repo provides "Source code to provide the LWJGL keyboard, mouse, and OpenGL APIs in a browser", "Source code for an OpenGL 1.3 emulator built on top of WebGL 2.0", "Utilities to decompile Minecraft 1.8 and apply patch files to it", "Browser-modified portions of Minecraft 1.8's open-source dependencies", and "Plugins for Minecraft servers to allow the eagler client to connect to them"; at that stage it "currently only supports multiplayer"; builds require Java 11+ and `CompileLatestClient.bat/.sh` opens a GUI installer; the repo deliberately excludes decompiled Minecraft source, resources and MCP config. — [Lingpand/webmc README (EaglercraftX README copy)](https://github.com/Lingpand/webmc)
- Later README (search excerpt): "The JavaScript runtime of EaglercraftX 1.8 is currently known to work on browsers as old as Chrome 38 on Windows XP, the game supports both WebGL 1.0 and WebGL 2.0"; dynamic lighting and PBR shaders "are not available in WebGL 1.0 mode or if floating point HDR render targets are not fully supported". — [EaglercraftX-1.8-workspace README (excerpt; URL now HTTP 451)](https://github.com/Eaglercraft-Archive/EaglercraftX-1.8-workspace/blob/master/EAGLERCRAFTX_README.md)
- The workspace keeps a desktop target that "will run the client using the JVM and an LWJGL3-based runtime, which can be useful for debugging crashes" without waiting for the JS or WASM-GC builds. — [EaglercraftX-1.8-workspace README (excerpt; URL now HTTP 451)](https://github.com/Eaglercraft-Archive/EaglercraftX-1.8-workspace/blob/master/EAGLERCRAFTX_README.md)
- The graphics layer is described as "a custom compatibility layer created by LAX1DUDE that lets the fixed function OpenGL 1.3 based rendering engine operate through an HTML5 WebGL canvas". — [EaglercraftX README mirror (excerpt)](https://purnhab68-gitea.hf.space/eymenwsmc/Eaglercraft-1.7.10/raw/branch/main/EAGLERCRAFTX_README.md)

**Networking: WebSocket proxy to real servers**
- "Due to restrictions it must use a custom proxy plugin which proxies the browser's Websocket connection to the pure TCP connection used by Minecraft." — [EaglercraftX README text as reproduced on a play page (excerpt)](https://nothingmake.duckdns.org/)
- EaglerXBungee is a BungeeCord/Waterfall *plugin*, not a fork, and is not compatible with the old 1.5 Bungee; install `EaglerXBungee-Latest.jar` in `plugins/`; players set a password with `/eagler` on vanilla 1.8; `online_mode=false` disables the password system (testing only). — [Lingpand/webmc README](https://github.com/Lingpand/webmc)
- EaglercraftXServer (a.k.a. EaglerXServer) is "an Eaglercraft plugin for Spigot, BungeeCord, and Velocity" supporting EaglercraftX 1.8, Eaglercraft 1.12.2 and Eaglercraft 1.5.2 clients, with "packet translator modules for legacy protocol versions (1.5, 1.6, beta, etc)"; its API is on a Maven repo as `net.lax1dude.eaglercraft.backend:api-bukkit:1.0.0`, requires Java 17, and plugins must `depend: [EaglercraftXServer]`. — [Modrinth: EaglercraftXServer](https://modrinth.com/mod/eaglercraftxserver); [CurseForge: EaglerXServer](https://www.curseforge.com/minecraft/bukkit-plugins/eaglerxserver); [termer/eaglerxserver mirror](https://git.termer.net/termer/eaglerxserver)
- Third-party hosting guide: the browser only ever talks `wss://` to the proxy; EaglerXServer inside the proxy "grabs the WebSocket traffic, and translates it into the old-school Minecraft TCP protocol the game server expects". — [Sealos: Eaglercraft client/server/gateway explained](https://sealos.io/blog/eaglercraft-client-server-gateway/)

**Networking: Shared Worlds (formerly LAN Worlds) via WebRTC + relay**
- Feature renamed from "LAN Worlds" to "Shared Worlds"; host presses Invite in the pause menu, gets a join code ("usually 5 letters"), joiner uses Direct Connect > Join Shared World; hidden=off also advertises the world to others on the same wifi like vanilla 1.8 LAN; if friends can't connect, "confirm everyone has the same set of shared world relay URLs configured". — [EaglercraftX README text as reproduced on a play page (excerpt)](https://nothingmake.duckdns.org/)
- The Java relay (EaglerSPRelay) is "a shared world connection manager that allows clients and servers to connect, exchange ICE candidates, descriptions, and session data via a relay system" — i.e. WebSocket signalling for WebRTC; roles are EaglerSPServer (host) and EaglerSPClient (joiner). — [EaglerRelayJS (JS reimplementation)](https://github.com/WebMCDevelopment/EaglerRelayJS); [EaglerSPPythonRelay](https://github.com/StoppedwummPython/EaglerSPPythonRelay)
- A client config lists default relays `relay.deev.is` ("lax1dude relay #1"), lax1dude relay #2 and an ayunami relay, picking the primary at random. — [client config in a hosted copy](https://huggingface.co/spaces/scratchmasterj21/minecraft/commit/0d984a467fea2a91cd01c8791b05e5ba8b8dab97)
- Integrated voice chat also uses WebRTC. — [HandWiki: Eaglercraft](https://handwiki.org/wiki/Software:Eaglercraft)

**Assets: `assets.epk`**
- Every Eaglercraft build ships an `assets.epk` "containing the compiled resources needed to run the game"; custom resources go in a `resources` folder (e.g. `lwjgl-rundir/resources`) and `epkcompiler/run.bat` regenerates the EPK; `ayunWebEPK` is a browser tool that decompiles EPKs. (Third-party fan-site description; format internals such as compression/CRC are claimed by one site only and unverified.) — [minecraftmaps.com: EPK files](https://www.minecraftmaps.com/minecraft-epk-files); [docs.fileformat.com: EPK](https://docs.fileformat.com/game/epk)
- The WASM-GC build produces an `assets.epw` bundle instead; build steps are `MakeWASMClientBundle` in `target_teavm_wasm_gc` and `CompileWASM` for `classes.wasm`; "There is no GUI for compiling the WASM-GC client at the moment." — [EaglercraftX README mirror (excerpt)](https://purnhab68-gitea.hf.space/eymenwsmc/Eaglercraft-1.7.10/raw/branch/main/EAGLERCRAFTX_README.md)

**WASM-GC runtime and the TeaVM fork**
- The WASM-GC client "uses a custom fork of TeaVM, the source is available at github.com/Eaglercraft-TeaVM-Fork/eagler-teavm" (branch `eagler-r1` referenced), buildable with `publishToMavenLocal`. — [EaglercraftX README mirror (excerpt)](https://purnhab68-gitea.hf.space/eymenwsmc/Eaglercraft-1.7.10/raw/branch/main/EAGLERCRAFTX_README.md)
- The fork repo (current branch `eagler-r3`) describes itself as "Fork of TeaVM for compiling EaglercraftX's WASM GC runtime"; the only listed change is "a heap grow callback added to TeaVM's new malloc/free implementation", with "no new API additions"; `eagler-r1` holds the original eagler malloc/free implementation. — [Eaglercraft-TeaVM-Fork/eagler-teavm](https://github.com/Eaglercraft-TeaVM-Fork/eagler-teavm)
- Status (README excerpt): the WASM-GC runtime is experimental, "still incompatible with several major browsers (especially Safari) and will not run in Chrome unless you can access the chrome://flags menu or request an origin trial token"; it "depends on JSPI, which will hopefully become enabled by default on the Chrome browser in the coming months"; it "performs significantly better than the JavaScript client, around 50% more FPS and TPS in some cases". — [EaglercraftX README mirror (excerpt)](https://purnhab68-gitea.hf.space/eymenwsmc/Eaglercraft-1.7.10/raw/branch/main/EAGLERCRAFTX_README.md)

### Inferences
- The legally relevant distinction for Spiral Knights: Eaglercraft's exposure came from distributing decompiled Mojang code and assets; the tooling itself (TeaVM, the LWJGL shim, the GL emulator, the WebSocket proxy pattern) was never the target and is reusable. A port of a game whose engine (Clyde) is open-source and whose rights holder cooperates is a different legal posture entirely.
- Eaglercraft's architecture is the template a TeaVM route would copy: (1) a `Platform*` abstraction replacing LWJGL (`Display`/`Keyboard`/`Mouse`/GL/AL), (2) a GL emulation layer turning legacy GL into WebGL2 draw calls, (3) a WebSocket-to-TCP gateway beside the game server, (4) a single HTML/JS bundle plus an asset archive fetched at start. The reported "about a month" for the LWJGL rewrite is for Minecraft 1.5.2's fixed-function usage; a GL20/GL30 shader-based engine is a smaller mapping problem for draw calls but a larger one for shader-source translation.
- The ~50% FPS/TPS gain of WASM-GC over JS output, combined with the fact that it needed JSPI and Chrome flags, implies that in 2025 lax1dude's WASM-GC build used JSPI (stack switching) rather than TeaVM's CPS coroutines for blocking; upstream TeaVM instead implemented coroutines natively in Wasm GC in 0.13.0 (Nov 2025). Whether EaglercraftX has since rebased onto upstream 0.13+ is unknown.

### Gaps
- Could not retrieve the canonical EaglercraftX README or source tree (all mirrors 451/404/522). Specifically unconfirmed from primary sources: (a) that OpenAL is mapped to Web Audio and mouse capture to Pointer Lock (every browser port must, but I have no quote), (b) that singleplayer worlds are stored in IndexedDB and that the integrated server runs in a Web Worker (only low-quality sites say "browser local storage"), (c) the `assets.epk` binary format and `EPKCompiler`/`MakeOfflineDownload` details, (d) the exact `src/teavm`, `src/lwjgl`, `src/protocol-relay` layout. These would be the first things to verify by cloning `git.eaglercraft.rip/eaglercraft/eaglercraft-1.8` when it is reachable.
- No documentation of how Eaglercraft handles Minecraft 1.8's Netty networking thread, sound thread and download threads under TeaVM's green threads beyond the general TeaVM model.
- Eaglercraft 1.5.2's own architecture (original 2020 client) is covered only by HandWiki's summary (multiplayer-only, WebSocket, "EaglercraftBungee"); no primary doc fetched.

## KQ3. CheerpJ (Leaning Technologies) 3.x/4.x in 2026: how it differs, LWJGL/JNI/OpenGL, licensing, performance, startup, game examples

### Takeaway
CheerpJ 4.3 (21 Apr 2026) is a full OpenJDK (8/11/17-preview) JVM compiled from C++ to Wasm with an interpreter + JIT-to-JavaScript, running unmodified JARs with reflection, dynamic class generation, AWT/Swing and a virtual FS/network layer; it is the only route that runs LWJGL *unmodified*, via Wasm-compiled JNI modules plus gl4es (Browsercraft: unmodified Minecraft 1.2.5 `client.jar`). The costs are a commercial licence for anything beyond individuals/one-person companies (Small Business £100/dev/month; Community tier forbids self-hosting), vendor-only JNI toolchain so far, raw-TCP only via Tailscale, and vendor-only performance claims ("satisfactory on mid-range machines"). Java 21 and 5.0 have slipped past the original end-2025 target.

### Cited Findings

**Architecture and difference from TeaVM**
- CheerpJ is "a WebAssembly-based Java Virtual Machine for the browser"; the runtime is based on OpenJDK, written in C++ and compiled to Wasm/JS with Cheerp; two-tier execution: bytecode starts in an interpreter (also used for init and cold code) which collects profiles, then hot bytecode is JIT-compiled to optimized JavaScript with inlining and devirtualization; AWT/Swing windows become a hierarchy of HTML elements and canvases; same-origin HTTP(S) transparently uses `fetch`; general networking uses Tailscale (a VPN that uses WebSockets as transport), supporting private services, peer-to-peer and internet via an exit node; `native` methods can be implemented in JavaScript; `cheerpjRunLibrary` gives bidirectional interop. — [CheerpJ architecture docs](https://cheerpj.com/docs/explanation/architecture)
- CheerpJ 3.0 (1 Feb 2024) was a full rewrite that removed CheerpJ 2's AOT step in favour of JIT-only, which the vendor says had a "vastly positive" effect on startup; only Java 8 at that time; the Minecraft demo was then "incomplete. LWJGL support is partial, so rendering isn't accurate, though the game is playable enough to get in-game". — [CheerpJ 3.0 blog](https://labs.leaningtech.com/blog/cheerpj-3.0)
- CheerpJ 3.1: "up to CheerpJ 3.1 we could only offer the use of JavaScript natives as a workaround"; earlier attempts "manually implemented a small subset of the LWJGL JNI methods directly in JavaScript, but this method turned out to be extremely time consuming". — [CheerpJ 3.1 blog](https://labs.leaningtech.com/blog/cheerpj-3.1)
- CheerpJ 4.0: Java 8 and 11; unmodified JARs run from bytecode (obfuscated/encrypted JARs fine); file system = HTTP-served assets + IndexedDB persistent storage + JS data; clipboard via Clipboard API; window manager for multiple windows/apps; stress test = IntelliJ IDEA (~400 MB of JARs); three-call embedding (`cheerpjInit()`, `cheerpjCreateDisplay(800,600)`, `cheerpjRunJar(...)`); Library Mode via `cheerpjRunLibrary()` with async/await; **WebAssembly JNI modules** "loaded and executed dynamically, similarly to what happens on native platforms via shared libraries", built with "custom JNI headers and libraries designed for the CheerpJ JVM" that are "planned for general release so users can compile their own modules". — [CheerpJ 4.0 blog](https://labs.leaningtech.com/blog/cheerpj-4.0)
- CheerpJ 4.1 (28 May 2025): Java 17 preview ("a preview of the stable support that is still scheduled for a future CheerpJ 5.0 release, expected before the end of 2025"); "Improved networking stack"; Java 11 gains SSL and audio; roadmap for 5.0: stable Java 17, npm support, "extended native JNI module support (JavaFX, SWT, and user-built JNI modules for any Java library)". — [CheerpJ 4.1 blog](https://labs.leaningtech.com/blog/cheerpj-4.1)
- CheerpJ 4.3 (21 Apr 2026): "focuses on stability and user experience"; file upload icon on decorated windows; `/files/downloads/` auto-download; long-press as hover for Swing on mobile; Java 8, 11, 17 supported; "Java 21 support is planned for later this year"; 5.0 "on the horizon". — [CheerpJ 4.3 blog](https://labs.leaningtech.com/blog/cheerpj-4.3)
- Original roadmap: Java 17 in 5.0 by end-2025, Java 21 in 6.0 by early 2026 with four OpenJDK builds (8/11/17/21). As of Oct 2026 neither 5.0 nor 6.0 has shipped. — [CheerpJ roadmap](https://cheerpj.com/our-roadmap-for-modern-java-in-the-browser/); [CheerpJ 4.3 blog](https://labs.leaningtech.com/blog/cheerpj-4.3)
- Secondary commentary (Apr 2026) claims enterprise feedback pushed WasmGC and startup performance ahead of Java 21 parity for 5.0; treat as speculation. — [bytecode.news on CheerpJ 4.3](https://bytecode.news/posts/2026/04/cheerpj-4-3-webassembly-based-jvm-for-the-browser)
- FAQ: reflection supported; dynamic class generation supported; runtime components download on demand; filesystem over HTTP (404s for probes are expected); JAR paths must be under `/app/`; "Browsers don't provide raw sockets, so RuneScape doesn't work yet" (a paid tunnelling add-on for the Applet Runner is mooted); to self-host the runtime you must contact Leaning Technologies; the runtime is served from a CDN domain. — [CheerpJ FAQ](https://cheerpj.com/docs/faq)
- JS natives: implement `Java_<fqcn>_<method>` functions and pass them via the `natives` option of `cheerpjInit`; `System.loadLibrary` resolves through `java.library.path` set in `javaProperties`. — [Implementing native methods](https://cheerpj.com/docs/guides/implementing-native-methods); [Implementing native libraries](https://cheerpj.com/docs/guides/implementing-native-libraries)
- Threads: the only threading doc found is the deprecated CheerpJ 2 Web Workers guide (message passing, no shared memory, primitives/arrays only). No CheerpJ 3/4 document describing how `java.lang.Thread` is scheduled was found. — [CheerpJ 2 Web Workers guide](https://labs.leaningtech.com/cheerpj2/guides/Using-web-workers)

**Browsercraft (Minecraft in CheerpJ)**
- Runs Minecraft **1.2.5**; "The original client.jar is fetched directly from Mojang servers on the end-user browser and runs unmodified"; LWJGL unmodified from Maven; LWJGL's "JNI methods which provide direct access to each and every method exposed by OpenGL... written in C and automatically generated by the LWJGL build system" are loaded as JNI Wasm modules; **gl4es** bridges OpenGL to GLES/WebGL; sessions intentionally limited to 3 minutes; repo `github.com/leaningtech/browsercraft`, demo `browsercraft.cheerpj.com`; "not based on decompilation or reverse engineering". — [Browsercraft showcase](https://labs.leaningtech.com/showcase/browsercraft); [CheerpJ 4.0 blog](https://labs.leaningtech.com/blog/cheerpj-4.0)
- Performance claim (vendor): Minecraft is "a notoriously inefficient and resource intensive application, so we consider it to be a stress test"; "thanks to recent improvements in our JIT compiler, the demo can now run with satisfactory performance on most mid range machines". No FPS figures. — [CheerpJ 4.1 blog](https://labs.leaningtech.com/blog/cheerpj-4.1)

**Licensing**
- CheerpJ Core tiers: Community (free; personal, FOSS, evaluations; commercial use allowed for individuals and one-person companies; self-hosting and OEM/redistribution NOT included), Small Business (£100 per developer per month, teams up to 10, commercial use, self-hosting and OEM/redistribution available), Enterprise (custom; any size; self-hosting included). Core is licensed per application, annual; perpetual Enterprise licences get 4 years of updates; discounts for non-profit/academic/public sector. — [CheerpJ licensing](https://cheerpj.com/licensing/)
- The free tier therefore implies loading the runtime from Leaning Technologies' CDN (self-hosting requires contacting them). — [CheerpJ FAQ](https://cheerpj.com/docs/faq); [CheerpJ licensing](https://cheerpj.com/licensing/)

**Startup / size (older data, flagged)**
- CheerpJ 2 guide: "most of the loading time is spent downloading the jar.js file(s)"; the runtime "totalling 10-20MB of data for a typical download"; all components cached by the browser. CheerpJ 3 removed jar.js entirely, so these numbers are indicative only. — [CheerpJ 2 startup guide (deprecated)](https://labs.leaningtech.com/cheerpj2/guides/Startup-time-optimization)
- CheerpJ 3 announcement: the old model's startup cost came from "many jar and jar.js files being downloaded, parsed and executed at runtime"; CheerpJ 3 uses "a fast interpreter for rarely used code" plus a JIT for hot code. — [Announcing CheerpJ 3](https://labs.leaningtech.com/blog/announcing-cheerpj-3)
- 2020 press on CheerpJ 2.0 noted apps "may still exhibit a perceptible waiting time for users to start using the application". — [InfoQ on CheerpJ 2.0](https://www.infoq.com/news/2020/04/cheerpj-wasm-java-compiler/)

### Inferences
- CheerpJ is the only option where Clyde + LWJGL 2 could in principle run with zero Java-side changes: LWJGL 2's `lwjgl.jar` plus its JNI natives (`liblwjgl`) compiled as a CheerpJ Wasm JNI module, with gl4es translating GL11..GL30 + desktop GLSL to WebGL. Browsercraft demonstrates exactly that stack for LWJGL 2 (Minecraft 1.2.5 used LWJGL 2.x). The blocker is that the JNI toolchain (headers/libs) was "planned for general release" in 4.0 and 4.1 and I found no announcement that it has shipped; today only the vendor can build such a module.
- TCP to the game server is not solvable in CheerpJ without either (a) Tailscale (a per-user VPN login, unsuitable for a public game) or (b) rewriting the game's socket layer to a WebSocket anyway, which erodes the "unmodified JAR" benefit. A same-origin WebSocket-to-TCP gateway (the Eaglercraft pattern) is still required.
- Licensing: a free-to-play MMO run by a company is not "personal/one-person", so expect at least the Small Business tier or Enterprise, and self-hosting the runtime (needed for a game CDN) is a paid feature.
- Because the whole OpenJDK runtime is downloaded on demand and bytecode is interpreted first, cold start for a large game will be noticeably slower than a TeaVM build whose output is a dead-code-eliminated, pre-optimised JS/Wasm bundle; no public numbers exist to quantify this for a 3D game.

### Gaps
- No documentation found on CheerpJ 3/4's `java.lang.Thread` implementation (single-threaded green threads vs Workers + SharedArrayBuffer). This matters for background loader threads and must be asked of the vendor.
- No public toolchain, docs or SDK for building user JNI Wasm modules was found; status of "general availability of JNI headers" is unknown.
- No independent performance or startup benchmarks for Browsercraft or any 3D game under CheerpJ; no memory-ceiling data.
- No Hacker News thread was surfaced by search for CheerpJ 3/4 (the search returned none).
- No evidence of any RuneScape-like or other commercial 3D game shipped on CheerpJ; the FAQ explicitly says RuneScape does not work for lack of raw sockets.

## KQ4. Other options: JWebAssembly, Bytecoder, J2CL/GWT, Kotlin/Wasm, GraalVM Web Image; realism for a big dependency tree

### Takeaway
None of the alternatives is realistic for a large LWJGL game today: GraalVM Web Image (Oracle GraalVM 25.1+, `native-image --tool:svm-wasm`) is officially experimental with multithreading "hampered" and multi-tens-of-MB outputs; J2CL's Wasm backend is experimental, Bazel-only and source-based; Kotlin/Wasm is Beta and does not consume Java bytecode; JWebAssembly lacks exceptions, threads and reflection; Bytecoder is stuck at Java 8-20 with no releases listed and its libGDX backend is archived.

### Cited Findings
- **GraalVM Web Image**: "takes a JVM application, performs ahead-of-time (AOT) compilation using GraalVM Native Image, and produces a WebAssembly module" plus a JS wrapper; enabled with `--tool:svm-wasm` as the first `native-image` argument; requires Oracle GraalVM 25.1 or later and Binaryen 119+ (`wasm-as`) on PATH; outputs `app.js`, `app.js.wasm`, `app.js.wat`; uses Wasm GC, Exception Handling and Typed Function References (Wasm 3.0); Node needs `--experimental-wasm-exnref` before Node 25; cannot run under wasmtime (depends on JS imports); "Web Image is an experimental technology and under active development"; "best suited for application-style builds hosted by a JavaScript runtime". — [GraalVM Web Image docs](https://www.graalvm.org/dev/reference-manual/web-image/)
- The Wasm backend was publicised in April 2025 ("GraalVM now benefits from a WebAssembly (Wasm) backend"). — [The New Stack](https://thenewstack.io/graalvm-finally-gets-java-for-webassembly/)
- A developer report (secondary; page could not be fetched, quoted via search) says "not all JVM features are currently supported (multithreading, for instance, is hampered by WebAssembly limitations)", reflection is configured via `reflect-config.json`, and a Drools demo compiled to a 41 MB `.wasm`. — [Kitemetric: GraalVM + WASM](https://kitemetric.com/blogs/graalvm-wasm-a-new-dawn-for-j2cl-gwt-developers)
- GraalWasm (a Wasm *runtime* embedded in Java) is a different product and irrelevant here. — [GraalVM 25 release notes coverage](https://www.infoworld.com/article/4061937/graalvm-25-arrives-backed-by-jdk-25.html)
- **J2CL / J2Wasm**: the Wasm backend "transpiles Java to WebAssembly", is experimental, developed with the Chrome team, based on Wasm GC, requires Chrome 119+ and Bazel; J2CL compiles Java *source*, not bytecode. — [J2CL getting-started-j2wasm](https://github.com/google/j2cl/blob/master/docs/getting-started-j2wasm.md)
- **Kotlin/Wasm**: "Although Kotlin/Wasm is still in Beta" (page dated 1 Sep 2026); targets `wasm-js` (browser) and WASI; requires browsers supporting Wasm GC and legacy exception handling; nothing about consuming Java libraries/bytecode. — [Kotlin/Wasm overview](https://kotlinlang.org/docs/wasm-overview.html)
- Kotlin's documented WasmGC browser floor: Chrome 119+, Firefox 120+, Safari/WebKit 18.2+ work by default; older Safari "Not supported". — [Kotlin/Wasm configuration](https://kotlinlang.org/docs/wasm-configuration.html)
- **JWebAssembly**: Java bytecode to Wasm, "1:1 conversion" without its own GC; "feature complete for milestone 1. There is a release candidate"; Java 8 tested; not yet supported (planned "3.0"): exception handling, multithreading, reflection, built-in GC (currently a JS polyfill); Releases section empty; "File access and sockets will not work in the browser". — [i-net-software/JWebAssembly](https://github.com/i-net-software/JWebAssembly)
- **Bytecoder**: Java bytecode to JS/Wasm/OpenCL; "Supports Java 8 up to Java 20", "Backed by OpenJDK 20 as JRE Classlib"; no releases listed on the repo page; 26 open issues. — [mirkosertic/Bytecoder](https://github.com/mirkosertic/Bytecoder)
- The Bytecoder libGDX backend is archived, and its maintainers pointed to gdx-teavm as "the most viable option to use libgdx-kotlin in the browser as of now". — [squins/gdx-backend-bytecoder](https://github.com/squins/gdx-backend-bytecoder/)
- **GWT** (for completeness): libGDX's official HTML5 backend is GWT-based, source-input, WebGL 1.0 only, "Multithreading is not supported", `System.nanoTime` unsupported, reflection restricted to libGDX's own utilities. — [libGDX HTML5/GWT specifics](https://libgdx.com/wiki/html5-backend-and-gwt-specifics)

### Inferences
- GraalVM Web Image is the one alternative worth re-checking in 12-18 months: it reuses the Native Image closed-world analysis and `reflect-config.json` discipline, which a Clyde port would need anyway, and Oracle's backing is credible. Today its experimental status, unclear thread story and large module sizes make it a research spike, not a plan.
- Source-based tools (GWT, J2CL) are poor fits because Clyde/Narya/Spiral Knights' dependency tree includes compiled third-party JARs; bytecode-based tools (TeaVM, CheerpJ) do not need source.

### Gaps
- No official GraalVM Web Image limitations page was found (threads, JNI, reflection specifics); the 41 MB and "multithreading hampered" claims come from one secondary blog.
- Bytecoder/JWebAssembly last-commit dates were not visible on the fetched pages; maintenance status is unconfirmed.

## KQ5. The LWJGL-to-web gap: LWJGL 2 vs 3, projects that re-implemented LWJGL on WebGL, libGDX gdx-teavm precedent, legacy/fixed-function GL on WebGL2

### Takeaway
There is no reusable, general-purpose "LWJGL on WebGL" library; every successful port either (a) re-implemented the subset of LWJGL/GL the game actually uses on top of WebGL2 via TeaVM JSO (Eaglercraft, gdx-teavm, the jME web port) or (b) ran real LWJGL JNI through gl4es inside CheerpJ (Browsercraft). Fixed-function GL is handled by writing an emulator that batches into shader-based WebGL2 draws; GL30 features map directly onto WebGL2 (ES 3.0), while WebGL1 fallbacks lose float render targets and more.

### Cited Findings
- LWJGL 3.4.1 (3 Feb 2026) is the current LWJGL; LWJGL 3 binds OpenGL through generated native bindings, with no web target; the "LWJGL alone doesn't cover web targets" point appears in third-party analysis that recommends libGDX for web via GWT or TeaVM. — [LWJGL 3 releases](https://github.com/LWJGL/lwjgl3/releases); [scratch-for-java PR analysis](https://ithub.global.ssl.fastly.net/openpatch/scratch-for-java/pull/16)
- Eaglercraft: hand-rewritten LWJGL (keyboard, mouse, OpenGL APIs) and an "OpenGL 1.3 emulator built on top of WebGL 2.0" with WebGL 1.0 fallback; shader features gated on WebGL2 + float HDR render targets. — [Lingpand/webmc README](https://github.com/Lingpand/webmc); [EaglercraftX-1.8-workspace README (excerpt; now 451)](https://github.com/Eaglercraft-Archive/EaglercraftX-1.8-workspace/blob/master/EAGLERCRAFTX_README.md)
- Browsercraft: unmodified LWJGL JNI C code compiled to a CheerpJ Wasm JNI module; gl4es "provides a compatibility layer between OpenGL, used by Minecraft, and GLES as provided by WebGL". — [CheerpJ 4.0 blog](https://labs.leaningtech.com/blog/cheerpj-4.0)
- **gdx-teavm** (xpenatan): libGDX backend that "uses TeaVM behind the scene to convert Java/Kotlin bytecode to Javascript"; targets JS and Wasm web builds, TeaVM-C native builds (GLFW, Android, experimental iOS); artifacts `com.github.xpenatan.gdx-teavm:backend-web`, Gradle plugin `com.github.xpenatan.gdx-teavm` with `js {}` / `wasm {}` blocks and `gdx_teavm_web_js_run` / `gdx_teavm_web_wasm_run` tasks; Apache-2.0. — [gdx-teavm README](https://github.com/xpenatan/gdx-teavm/blob/master/README.md); [Maven Central backend-teavm](https://central.sonatype.com/artifact/com.github.xpenatan.gdx-teavm/backend-teavm)
- gdx-teavm README limitations: "Reflection support is very small so only reflection used in tests will work"; "TeaVM does not support every class methods from java package or JNI native methods"; native libs (Box2D, Bullet, ImGui, PhysX, FreeType) "use emscripten and jParser to convert C++ to Javascript/WebAssembly". — [gdx-teavm README via JitPack mirror](https://jitpack.io/p/xpenatan/gdx-dragome-backend)
- gdx-teavm releases: 1.6.2 (24 Aug 2026; TeaVM 0.15.0 / libGDX 1.14.2) made `useGL30` default to `true` with automatic WebGL1 fallback, `isGL30Available()` reports real context state, fixed partial NIO-buffer uploads on Wasm; 1.6.1 (27 Jul 2026) expanded `glGetIntegerv` and texture-parameter queries, added an instancing example exercising GL30, persistent dev server for JS and Wasm, Wasm optimisation default `BALANCED`; 1.6.0 (15 Jul 2026) first-class Gradle plugin, C/native backends, Java 17 required, `wasm {}` target added; 1.5.5 (7 May 2026) on TeaVM 0.14.0; 1.5.4 (15 Mar 2026) fixed international keyboard layouts/numpad and "improves WebGPU support"; 1.5.2 (1 Mar 2026) on TeaVM 0.13.1. GL31/GL32 are never mentioned. — [gdx-teavm releases](https://github.com/xpenatan/gdx-teavm/releases)
- gdx-teavm web runtime details: Wasm strict mode requires `@JSClass(transparent = true)` for JS facade types without a real global constructor "such as `WebGL20.CustomIntMap`" (i.e. the GL layer is a JSO facade over WebGL named `WebGL20`); asset manifest is compiled into a generated runtime class; dev server auto-reloads over a WebSocket; libraries declare bundled resources in `META-INF/gdx-teavm.properties`. — [gdx-teavm backend-architecture.md](https://github.com/xpenatan/gdx-teavm/blob/master/docs/backend-architecture.md)
- **jMonkeyEngine web port** (RiccardoBlb, 13 Aug 2023, `github.com/riccardobl/webmonkeyengine`, module `jme3-web`): rendering "Ported to WebGL 2 (GL ES 3)"; audio "Ported to WebAudio" (only predefined reverb environments, impulse responses from reverbjs.org); mouse/keyboard/touch OK, joystick not supported; jme3-jbullet "ported to Ammo.js (bullet emscripten build)"; jme3-networks not supported ("needs a WebSocket connector"; TeaVM already provides client WebSocket bindings); jme3-awt-dialogs not supported (needs an HTML port); main rendering bug was `GLImageFormats` mapping RGB8 to RGB565 which desktop drivers silently upgraded but mobile/AMD exposed; all resources fetched over HTTP, prefetch filters were added then removed as "unreliable"; build `./gradlew --no-daemon compileJava generateJavaScript copyAllResources generateResourcesIndex` (without `--no-daemon` builds were partially cached/broken); secure context (HTTPS/localhost) needed for some HTML5 APIs. — [jME TeaVM port thread](https://hub.jmonkeyengine.org/t/porting-jmonkeyengine-to-the-browser-with-webgl2-and-teavm-sourcecode-released/47020)
- libGDX GWT backend (the older precedent for "re-target a Java framework's GL layer to WebGL"): WebGL 1.0 only; NPOT textures cannot use mipmaps or repeat; must check `supportsExtension` before enabling shader extensions; some `Pixmap` methods unsupported; audio needs a user gesture before first playback; fullscreen not on iOS. — [libGDX HTML5/GWT specifics](https://libgdx.com/wiki/html5-backend-and-gwt-specifics)

### Inferences
- Mapping for the Spiral Knights profile under a TeaVM route: `Display` -> canvas + rAF loop + resize/fullscreen API; `Keyboard`/`Mouse` -> DOM key/mouse events with Pointer Lock for relative mouse (every browser game does this; Eaglercraft's primary text not retrievable); `GL11`..`GL20` -> a Java facade whose methods call `WebGL2RenderingContext` through TeaVM JSO (what gdx-teavm's `WebGL20` and Eaglercraft's emulator do); `GL30` VAOs/FBOs/instancing -> native WebGL2 (gdx-teavm 1.6.2 now defaults to GL30 on WebGL2); `AL10` -> Web Audio `AudioContext`/`PannerNode` (jME precedent); desktop GLSL 1.10/1.20 shaders -> must be rewritten or auto-translated to GLSL ES 3.00 (`#version 300 es`, `in/out`, precision qualifiers, texture() instead of texture2D()). gl4es does this translation automatically in the CheerpJ route; in the TeaVM route it is manual or a custom preprocessor.
- Any fixed-function usage in Clyde (matrix stack, `glBegin/glEnd`, `glEnable(GL_LIGHTING)`, fog) has no WebGL2 equivalent and needs an emulator of the Eaglercraft kind (uniform-based matrix stack + generated shader permutations); a shader-based engine minimises this but legacy debug/UI paths often still use immediate mode.
- The two-year-old jME port shows what breaks in a 3D Java engine on TeaVM beyond GL: reflection-driven asset loaders, AWT dialogs/fonts, networking, physics natives, and precision/format assumptions that only surface on mobile GPUs.
- gdx-teavm's cadence (five releases Feb-Aug 2026 tracking TeaVM 0.13.1 -> 0.15.0) is a healthy sign that TeaVM's WebGL/JSO path is being exercised by shipping games.

### Gaps
- No project named "lwjgl-web" or any standalone LWJGL-2/3-API-compatible WebGL implementation was found; the only LWJGL re-implementations are embedded in Eaglercraft's (DMCA-blocked) tree.
- Could not read gdx-teavm's actual GL facade source (`WebGL20`, GL30 implementation) to list unsupported `GL20`/`GL30` methods; and the libGDX GL API is already a GLES-shaped subset, so it is not a 1:1 proxy for the LWJGL 2 `GL11..GL30` static API surface.
- No source quantifies the desktop-GLSL-to-ESSL translation burden for any of these ports.

## KQ6. Java 2D / AWT / Swing under TeaVM and CheerpJ

### Takeaway
TeaVM has no `java.awt`, `java.awt.image`, `javax.imageio` or `javax.sound` at all and its docs send Swing users to CheerpJ; CheerpJ implements AWT/Swing (and by extension Java2D) by rendering windows into HTML elements and canvases with third-party look-and-feels working. Any AWT use in the game (image decode, fonts, dialogs) must be rerouted to browser APIs on the TeaVM route and simply works, at a performance cost, on CheerpJ.

### Cited Findings
- TeaVM's JCL report lists no `java.awt`, `java.awt.image`, `javax.imageio` or `javax.sound` packages. — [TeaVM JCL report](https://teavm.org/jcl-report/recent/jcl.html)
- TeaVM overview: for tightly coupled Swing apps "look elsewhere" and consider CheerpJ. — [TeaVM overview](https://teavm.org/docs/intro/overview.html)
- CheerpJ: "AWT and Swing windows are converted into a hierarchy of HTML elements and HTML5 canvases"; third-party Look&Feel, multi-window, keyboard focus and clipboard supported; 4.3 adds touch/long-press support for Swing menus on phones. — [CheerpJ architecture](https://cheerpj.com/docs/explanation/architecture); [CheerpJ 4.3 blog](https://labs.leaningtech.com/blog/cheerpj-4.3)
- jME web port: `jme3-awt-dialogs` "not supported (needs an HTML port)". — [jME TeaVM port thread](https://hub.jmonkeyengine.org/t/porting-jmonkeyengine-to-the-browser-with-webgl2-and-teavm-sourcecode-released/47020)
- libGDX GWT: some `Pixmap` methods (e.g. loading from binary data) unsupported; lines are antialiased by the canvas. — [libGDX HTML5/GWT specifics](https://libgdx.com/wiki/html5-backend-and-gwt-specifics)
- TeaVM JSO exposes browser APIs including `File`/`Blob` reading (0.11.0), WebGPU (0.16.0) and, per the jME port, WebSocket. — [TeaVM releases](https://github.com/konsoletyper/teavm/releases); [jME TeaVM port thread](https://hub.jmonkeyengine.org/t/porting-jmonkeyengine-to-the-browser-with-webgl2-and-teavm-sourcecode-released/47020)

### Inferences
- On TeaVM, image loading becomes `Image`/`createImageBitmap` + `texImage2D` from an `HTMLImageElement`/`ImageBitmap` (no CPU-side `BufferedImage`), text rendering becomes canvas 2D `fillText` into a texture atlas or a prebuilt bitmap-font pipeline, and any `java.awt.Font` metrics code must be replaced. Native-window dialogs become HTML overlays.
- A game that only uses AWT for offline asset preparation (e.g. tooling) is unaffected if that code is excluded from the web build; whole-program DCE will drop it if nothing reachable references it.

### Gaps
- No documentation on CheerpJ's Java2D rasteriser performance for texture-upload style workloads (drawing to a `BufferedImage` and uploading to GL every frame).

## KQ7. Practical: bundle sizes, load times, memory ceilings, lazy loading, debugging, build pipeline

### Takeaway
Concrete numbers are scarce: TeaVM output is whole-program DCE'd (no official size data; Wasm GC modules are a few percent smaller after 0.15), CheerpJ's runtime was 10-20 MB in the CheerpJ 2 era and now streams components on demand, and GraalVM Web Image produced a 41 MB module for a mid-size app. TeaVM's debugging story is source maps + IDEA (JS only) and a stack deobfuscator for Wasm GC; CheerpJ needs no build step at all; all routes need assets fetched over HTTP with an explicit preload/lazy strategy because class-level lazy loading does not exist in AOT output.

### Cited Findings
- TeaVM Wasm GC: `local.tee` lowered module size "up to about 1%"; direct buffers pass to JS without copying; linear memory `maxSize` default 2 GiB; shared memory requires COOP/COEP. — [TeaVM releases](https://github.com/konsoletyper/teavm/releases); [Wasm GC loader API](https://www.teavm.org/docs/wasm-gc-backend/loader.html)
- TeaVM debugging: source maps + IDEA plugin (JS backend); gdx-teavm notes IDEA debugging is JavaScript-only and that generated `app.js` frames and `js:` temporaries leak into the debugger; Wasm GC uses `stackDeobfuscator` to map addresses to Java lines. — [TeaVM overview](https://teavm.org/docs/intro/overview.html); [gdx-teavm usage.md](https://github.com/xpenatan/gdx-teavm/blob/master/docs/usage.md); [Wasm GC loader API](https://www.teavm.org/docs/wasm-gc-backend/loader.html)
- TeaVM build integration: Gradle plugin `org.teavm` (dev server, config-cache support, `debug` switch since 0.15), Maven plugin with toolchain support (0.16), IDEA plugin; gdx-teavm wraps these in `gdxTeaVM { assets("assets"); js {}; wasm {} }` and copies assets into a compiled preload manifest. — [TeaVM releases](https://github.com/konsoletyper/teavm/releases); [gdx-teavm README](https://github.com/xpenatan/gdx-teavm/blob/master/README.md)
- Eaglercraft's desktop LWJGL3 runtime exists specifically because debugging crashes on the JVM is faster than waiting for JS/WASM-GC builds. — [EaglercraftX-1.8-workspace README (excerpt; now 451)](https://github.com/Eaglercraft-Archive/EaglercraftX-1.8-workspace/blob/master/EAGLERCRAFTX_README.md)
- CheerpJ: no build step (three JS calls), runtime components "download on demand to reduce total download size", filesystem over HTTP with IndexedDB persistence, 10-20 MB typical runtime download in the CheerpJ 2 era, browser-cached thereafter; IntelliJ (~400 MB JARs) is the vendor's stress test. — [CheerpJ 4.0 blog](https://labs.leaningtech.com/blog/cheerpj-4.0); [CheerpJ FAQ](https://cheerpj.com/docs/faq); [CheerpJ 2 startup guide](https://labs.leaningtech.com/cheerpj2/guides/Startup-time-optimization)
- GraalVM Web Image: 41 MB `.wasm` for a Drools demo (secondary). — [Kitemetric](https://kitemetric.com/blogs/graalvm-wasm-a-new-dawn-for-j2cl-gwt-developers)
- libGDX GWT preloader fetches every file in the asset directory up front, "which can take a long time on slow connections"; an `AssetFilter` can defer non-essential files but those must then go through `AssetManager` or the game freezes; `html:dist` source maps are "usually a few MB". — [libGDX HTML5/GWT specifics](https://libgdx.com/wiki/html5-backend-and-gwt-specifics)
- jME port: all resources fetched over HTTP add latency; regex prefetch lists were tried and dropped in favour of browser caching. — [jME TeaVM port thread](https://hub.jmonkeyengine.org/t/porting-jmonkeyengine-to-the-browser-with-webgl2-and-teavm-sourcecode-released/47020)
- Eaglercraft ships all game resources as one `assets.epk` (or `assets.epw` for WASM-GC) and the whole client is meant to run from a single HTML file. — [minecraftmaps.com: EPK files](https://www.minecraftmaps.com/minecraft-epk-files); [HandWiki: Eaglercraft](https://handwiki.org/wiki/Software:Eaglercraft)
- Browser floor for Wasm GC output (Kotlin's documented numbers, applicable to any WasmGC producer): Chrome 119+, Firefox 120+, Safari 18.2+. TeaVM's JS backend runs far older browsers (Eaglercraft's JS build: Chrome 38). — [Kotlin/Wasm configuration](https://kotlinlang.org/docs/wasm-configuration.html); [EaglercraftX-1.8-workspace README (excerpt)](https://github.com/Eaglercraft-Archive/EaglercraftX-1.8-workspace/blob/master/EAGLERCRAFTX_README.md)

### Inferences
- Lazy loading of *code* is not available on TeaVM (closed-world AOT, class loaders restricted) or GraalVM; the lever is lazy loading of *assets* over HTTP plus IndexedDB caching, which maps well onto a game whose assets already live in a resource bundle. CheerpJ is the exception: it loads JARs/classes on demand from its HTTP filesystem.
- For a game of Spiral Knights' size, shipping two builds (TeaVM JS for reach, TeaVM Wasm GC for performance on 2024+ browsers) is cheap because both come from the same compiler and the same Java platform layer; gdx-teavm already does exactly this with `js {}` and `wasm {}` targets, and Eaglercraft does it with separate `target_teavm_javascript` and `target_teavm_wasm_gc` outputs.
- Memory ceiling: TeaVM Wasm GC objects live in the engine's GC heap (no fixed cap documented) while direct NIO buffers live in linear memory capped by `maxSize` (default 2 GiB); the JS backend is bounded by the JS heap. Neither vendor documents a practical limit; browsers' per-tab limits dominate.

### Gaps
- No published output-size or load-time measurements for any TeaVM 3D game build (Eaglercraft bundle size not retrievable; gdx-teavm publishes none).
- No CheerpJ 3/4 runtime-size or cold-start figures.
- No data on IndexedDB quota handling in any of these runtimes.
