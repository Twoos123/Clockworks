# The 2023–Oct 2026 wave of big-name PC/console games ported to the browser, and how it is done

Research date: 2026-10-12. Scope: concrete, named browser-port projects of commercial games (source-release, leaked-source, decompilation, reimplementation, or binary translation), the toolchain each used, how assets are handled, where it is hosted, and author write-ups. Older foundational projects are included only where they are the template later ports copy.

## Key Question 1: Which specific games have been ported to the browser recently, and from what source / with what toolchain / asset model / hosting?

### Takeaway
There is now a large, fast-moving catalogue (two independent indexes list 40–50+ browser-playable commercial titles as of October 2026), dominated by C/C++ engines compiled with Emscripten to WebAssembly + WebGL2, with the user supplying their own game data; a 2026 sub-wave adds WebGPU renderers (C&C Generals, DamnationX, PS2 recomp) and AI-assisted decompilation/porting, and several high-profile ports have been DMCA'd (GTA Vice City/DOS.Zone, Black Ops 2 clones, Eaglercraft, SM64).

### Cited Findings

**Indexes that track the wave (useful as living catalogues)**
- recompiledgames.com is an "Independent index" listing 52 browser/decomp projects with asset status ("Instant" vs "Own files") and play links; it hosts no games, says projects that include or stream assets or rebuild current commercial games carry the most legal risk, and warns users to avoid launchers/installers for browser ports — [Recompiled Games](https://recompiledgames.com/)
- SubmitGame/awesome-decomp-games has a "Play in your browser" section with 41 entries, tags 7 as "needs your game files" and others "free demo, no game files needed", re-checks links daily in a real browser and hides taken-down ones; last updated 2026-10-12 — [awesome-decomp-games](https://github.com/SubmitGame/awesome-decomp-games)

**Half-Life 1 / Counter-Strike 1.6 (GoldSrc via Xash3D-FWGS reimplementation)**
- yohimik/webxash3d-fwgs is a Lerna monorepo for compiling and running WebAssembly builds of Xash3D-FWGS (open-source GoldSource reimplementation) with Emscripten; ~161 stars/25 forks; published as npm packages `xash3d-fwgs` (engine wrapper, zero dependencies), `cs16-client` (Emscripten-compiled CS16-Client WASM binaries) and `hlsdk-portable` (Half-Life game module); usage is `new Xash3D({canvas})`, `init()`, `main()`, then console commands via `Cmd_ExecuteString("map de_dust2")` — [npm xash3d-fwgs](https://www.npmjs.com/package/xash3d-fwgs); [cs16-client package](https://github.com/yohimik/webxash3d-fwgs/tree/main/packages/cs16-client); [DeepWiki browser runtime architecture](https://deepwiki.com/yohimik/webxash3d-fwgs/3.1-browser-runtime-architecture)
- The HN thread "Run Half-Life Using HTML (and Counter-Strike 1.6)" shows the npm packages used to run Half-Life in a browser with assets loaded from jsDelivr CDN links — [HN 44656403](https://news.ycombinator.com/item?id=44656403)
- judealonzo/webxash is a frontend running HL1 and CS 1.6 on the Xash3d-FWGS WebAssembly build; its author "just wrote a frontend" and refers engine bugs upstream; multiplayer requires separately Docker-hosted servers with a websocket address on port 27016 by default — [judealonzo/webxash](https://github.com/judealonzo/webxash)
- Sades160/webxash3d-fwgs-improved (fork of yohimik's) lists lazy-loading game files "instead of loading everything into RAM" as a TODO, i.e. the stock port loads the whole `valve` folder into memory — [webxash3d-fwgs-improved](https://github.com/Sades160/webxash3d-fwgs-improved)
- x8BitRain/hl-engine-js is a JS module for playing Half-Life maps in the browser that relies on an older Xash3D-Emscripten port, with plans to rebase on the newer WASM build; its demo x8bitrain.github.io/webXash is tagged "free demo, no game files needed" — [hl-engine-js](https://github.com/x8BitRain/hl-engine-js); [awesome-decomp-games](https://github.com/SubmitGame/awesome-decomp-games)
- Pixelsuft's Half-Life build is hosted on GitHub Pages, user supplies own game files, single-player focus, data stored locally in the browser — [radiantoptimizergames guide (secondary)](https://radiantoptimizergames.com/half-life-in-browser/); [pixelsuft.github.io/hl listing](https://recompiledgames.com/)
- csjs.live runs CS 1.6 on the Xash3D FWGS engine as WebAssembly ("CSJS") with multiplayer — [Recompiled Games](https://recompiledgames.com/)
- Upstream FWGS has an open issue (#1226, ~1,350 days old) asking for WebAssembly to be an official compile target like Android; no official browser target was found — [FWGS issue 1226](https://github.com/FWGS/xash3d-fwgs/issues/1226)

**Quake 1 / 2 / 3, RTCW, Jedi Academy, Urban Terror (id Tech 2/3 GPL source)**
- The official ioquake/ioq3 README documents an Emscripten build: `emcmake cmake -S . -B build -DCMAKE_BUILD_TYPE=Release`, `cmake --build build`, copy baseq3 pk3s into build/Release/baseq3, only files listed in `client-config.json` load, serve with `python3 -m http.server`, open ioquake3.html — [ioquake/ioq3](https://github.com/ioquake/ioq3); forks jdarpinian/ioq3 (web-focused) and WofWca/ioq3 also carry Emscripten support — [jdarpinian/ioq3](https://github.com/jdarpinian/ioq3); older ports klaussilveira/ioquake3.js and quakejs build with `make PLATFORM=js` — [ioquake3.js](https://github.com/klaussilveira/ioquake3.js)
- Q3JS (lklacar/q3js, q3js.com): "Native ioquake3 gameplay compiled to WebAssembly with the OpenGL 2 renderer"; Emscripten SDK 6.0.5 + CMake + Ninja; TypeScript client; does not include or download proprietary Q3 data (user supplies pak0–pak8.pk3); multiplayer via a WebSocket-to-UDP gateway (ws://localhost:27961/ws, `Q3JS_SECURE` for wss); Quarkus/Java 17 master server with PostgreSQL; nginx static + Next.js site; 4,346 commits — [lklacar/q3js](https://github.com/lklacar/q3js)
- jk.q3js.com runs Star Wars Jedi Knight: Jedi Academy via OpenJK as WebAssembly, own files, multiplayer — [Recompiled Games](https://recompiledgames.com/)
- Pieter Levels' rtcw.pieter.com runs "the real RTCW multiplayer engine (iortcw) compiled to WebAssembly"; first load downloads ~380 MB of game data, cached afterwards — [rtcw.pieter.com](https://rtcw.pieter.com/)
- Levels' write-up (published 11 June 2026): started from iortcw MP; diffed the Wwasm single-player Emscripten port against clean SP to extract its `#ifdef EMSCRIPTEN` patch set and re-applied it by hand to the MP tree; GL4ES translates OpenGL 1.x to WebGL2 (fixed an "OpenGL 1.1 required" crash by calling `initialize_gl4es()` in MP's `R_Init`); re-enabled networking that Wwasm disables; patched out the 1.41 point-release check; built native `iowolfded` dedicated server from the same source as a systemd service on mp_beach; game data carved out of the 2001 CD ISO's Wise installer with `offzip` (pak0.pk3 316 MB, mp_pak0.pk3, UI pak); client fetches paks over HTTPS before engine boot via an Emscripten "run dependency" and mounts them with IDBFS so the ~380 MB downloads once; ~1 hour effective time using an AI coding tool — [levels.io](https://levels.io/ported-return-to-castle-wolfenstein-to-web-with-ai)
- Levels also runs q1.pieter.com (QuakeWorld, FTE QuakeWorld), q2.pieter.com (Quake II, multiplayer), q3.pieter.com and ut.pieter.com (Urban Terror, ioquake3-based); a March 2026 post is titled "Quake III server now runs in the browser 7 years later" — [awesome-decomp-games](https://github.com/SubmitGame/awesome-decomp-games); [levels.io](https://levels.io/ported-return-to-castle-wolfenstein-to-web-with-ai)
- Other Quake-family web engines: NetQuake.io (WebQuake), Qwasm2 (Quake 2 engine with WebGL 2 and software-rendered modes) — [Recompiled Games](https://recompiledgames.com/); [wasm-game topic](https://github.com/topics/wasm-game?o=asc&s=forks)
- 2026 outlier: "Show HN: Quake ported to safe Rust, playable in browser" (quake-srp, self-described "slop rust port"); commenters noted the C version already runs via WASM — [HN 50016312](https://news.ycombinator.com/item?id=50016312)

**Zelda: Ocarina of Time (OoT decomp → Ship of Harkinian → Emscripten)**
- zalo's Shipwright fork (zalo.github.io/Shipwright) is an Emscripten/WASM build of Ship of Harkinian running entirely client-side with WebGL rendering, in-browser ROM loading, URL-based configuration and multiplayer; prerequisites Emscripten SDK 3.1.64+, CMake 3.20+, Ninja; the README says upstream has no plans to merge web support; ROM not included — [zalo/shipwright-64 (sibling project, Mario in OoT via libsm64, web/WASM)](https://github.com/zalo/shipwright-64); [JDtoHTML/oot-cleanroom description of zalo's fork](https://github.com/lejiyo09/JDtoHTML)
- Project516/Shipwright PR #2 "Add a WebAssembly build" (merged Sep 26, 2026) is the most detailed public recipe: based on SoH 9.2.3 with a libultraship fork branch `soh-9.2.3-web` (GLES shader, canvas sizing, fullscreen, `/storage` fixes); emsdk 4.0.12 pinned in CI; SDL2/zlib/libpng from Emscripten ports; tinyxml2, nlohmann_json, spdlog, libzip, ogg, vorbis, opus, opusfile built with `-pthread`; no ROM bundled; `soh.o2r` built natively and preloaded; ZAPDLib extracts the player's ROM in the browser (files over 64 MB refused; copy written to /tmp then deleted); saves/config/extracted archives persist in IndexedDB synced via `/storage`; fixed pool of 8 pthread workers; Asyncify used for the game loop with an `asyncify-remove.txt` exclusion list; randomizer table files compiled at `-O0` because at `-O1+` each needed >4 GB RAM under exception handling; `-sBINARYEN_EXTRA_PASSES=-ocimfs=1000` caps inlining (otherwise one function reached 53,185 locals and the Asyncify link took 2–3 h; with the cap the web job takes ~53 min); `-sASYNCIFY_IGNORE_INDIRECT=1` ruled out because the first frame yield goes through indirect calls; `coi-serviceworker.js` for cross-origin isolation; Crowd Control/Sail/Anchor disabled (no raw sockets); GitHub Pages deploy on push to master; ~45 fps under software rendering in headless Chromium — [Project516/Shipwright PR 2](https://github.com/Project516/Shipwright/pull/2); PR #7 rebases the web port onto upstream 9.3.0 — [PR 7](https://github.com/Project516/Shipwright/pull/7)
- andrewnakas/oot-cleanroom uses zalo's Emscripten/WebGL fork with every ROM asset regenerated clean-room, so no ROM is needed; demo at andrewnakas.github.io/oot-cleanroom — [oot-cleanroom](https://github.com/andrewnakas/oot-cleanroom)
- Context: Harbour Masters' Ship of Harkinian uses libultraship (LUS) and requires a legally dumped ROM — [Wikipedia: Ship of Harkinian](https://en.wikipedia.org/wiki/Ship_of_Harkinian)

**Perfect Dark (n64decomp/perfect_dark → fgsfds PC port → web)**

**Command & Conquer: Generals Zero Hour (EA's 2025 GPL-3.0 source release → GeneralsX)**
- caiiiycuk/Generals-WebAssembly ("the real 2003 engine compiled to WebAssembly"): lineage ammaarreshi/Generals-Mac-iOS-iPad → Lolendor/Generals-WebAssembly → caiiiycuk fork, engine reached via fbraz3/GeneralsX from EA's GPL v3 release; Emscripten 4.x, CMake preset `emscripten`, Ninja, Python brotli, optional Go server; custom `d3d8webgl` Direct3D 8 → WebGL2 layer building on LostMyCode/d3d9-webgl; no assets included — user places their own copy (Steam app 2732960) under `web/gamedata/<build>/` and `pack-assets.sh` packs it into a GAXD `build.data` archive of 64 MB Brotli-q11 segments; client streams the archive, decompresses in a Web Worker with brotli-wasm and writes to OPFS (IndexedDB fallback), peak RAM ~130 MB for a ~2 GB payload; `web/dist/` is static (GitHub Pages / nginx / python http.server) with COOP/COEP injected client-side by a service worker; UDP transport bridged (`WebUDP.cpp` → `netbridge.js`) into a WebRTC peer mesh (host 10.77.0.1 relays, joiners 10.77.0.N), signaling via public MQTT-over-WebSocket brokers with room codes, STUN/TURN in `ice.json`; audio OpenAL → WebAudio; FFmpeg-wasm wired for video — [caiiiycuk/Generals-WebAssembly](https://github.com/caiiiycuk/Generals-WebAssembly)

### Inferences
- The dominant pattern in 2025–26 is not "new engine tech" but a convergence of (a) mature decomp/source-port codebases (SoH, DevilutionX, iortcw, reVC, GeneralsX), (b) Emscripten 4.x/6.x maturity (pthreads, WASMFS, OPFS, ports), and (c) AI coding agents that make the grind of swapping platform layers cheap — Levels' RTCW port, WebTTD, OpenBW web and the GunZ port all credit AI tools explicitly.
- Hosted "instant play" sites (pieter.com, csjs.live, q3js) are the ones that take on legal exposure by serving game data; GitHub-hosted projects almost universally adopt bring-your-own-files (file picker → OPFS/IndexedDB), and the two SM64 projects that got attention both retreated to BYO-ROM after takedown pressure.
- There is a visible migration from WebGL2 to WebGPU only where a project writes its own renderer (DamnationX HD art, ebellumat's Generals, PS2 recomp GS); ports that translate legacy GL1/D3D8/D3D9 calls still target WebGL2 via GL4ES or d3d9-webgl-style shims.

## Key Question 2: What is the general recipe, and where do porters consistently hit problems?

### Takeaway
The repeatable recipe is: obtain C/C++ source → ensure an SDL2/SDL3 platform layer → compile with Emscripten (`emcmake cmake`) using Emscripten ports for SDL/zlib/libpng → map legacy GL/D3D to WebGL2 via a shim (GL4ES, d3d9-webgl, Emscripten GLES2 emulation, or an engine-native GLES renderer like fast3d) → restructure the main loop (`emscripten_set_main_loop`, Asyncify, or pthreads + `PROXY_TO_PTHREAD`) → put user-supplied data into OPFS/IDBFS and saves into IndexedDB → serve statically with COOP/COEP (often via a service worker) → bridge UDP networking through WebSocket gateways or WebRTC meshes. Recurring pain points are threads/cross-origin isolation, Asyncify link cost and code size, the 4 GB wasm32 ceiling, timers/frame pacing, no raw sockets, and large data bundles that free static hosts will not serve.

### Cited Findings

**Platform layer and graphics**
- OpenRCT2 was practical to browserize because it uses SDL2 and Emscripten has an SDL2 port — [olydis Medium](https://olydis.medium.com/roller-coaster-tycoon-in-the-browser-ef6a340bced8)
- SoH's web build takes SDL2, zlib and libpng from Emscripten ports and pins emsdk 4.0.12; desktop code is gated behind `EMSCRIPTEN`/`__EMSCRIPTEN__` and `CMake/web.cmake` is only included under `emcmake` — [Shipwright PR 2](https://github.com/Project516/Shipwright/pull/2)
- GL4ES translates RTCW's OpenGL 1.x calls to WebGL2 — [levels.io](https://levels.io/ported-return-to-castle-wolfenstein-to-web-with-ai); Eaglercraft maps OpenGL 1.3 calls to WebGL 2.0 with a compatibility layer by LAX1DUDE — [mclist.io](https://mclist.io/knowledgebase/what-is-eaglercraft)
- Direct3D games keep their D3D calls and translate at runtime: GunZ via LostMyCode/d3d9-webgl (the author rejected a rewrite or transpiler) — [dev.to GunZ](https://dev.to/whiplash/how-i-fully-ported-a-heavily-windows-dependent-online-game-to-the-browser-with-webassembly-1fea); Generals via `d3d8webgl` built on d3d9-webgl, or "Dvijoke d8web" — [Generals-WebAssembly](https://github.com/caiiiycuk/Generals-WebAssembly); [GeneralsXWeb](https://github.com/meerzulee/GeneralsXWeb)
- FNA3D under Emscripten targets OpenGL ES 2.0 through Emscripten's emulation layer, with `-sMIN_WEBGL_VERSION=2` — [velzie blog](https://velzie.rip/blog/celeste-wasm)
- N64 decomps reuse libultraship's fast3d renderer (SoH, Perfect Dark web) — [perfect_dark_web](https://github.com/moeiscool/perfect_dark_web); the SoH web libultraship fork needed fixes for GLES shaders, canvas sizing and fullscreen — [Shipwright PR 2](https://github.com/Project516/Shipwright/pull/2)
- D3wasm used the WebGL subset of OpenGL ES 2.0 plus GLSL; Continuation Labs noted that a first attempt via a compatibility layer gave "ugly graphics and poor performance" before a proper renderer path — [DoomWiki](https://doomwiki.org/wiki/D3wasm); [Continuation Labs](http://www.continuation-labs.com/projects/d3wasm/)

**Main loop: set_main_loop vs Asyncify vs JSPI vs threads**
- Emscripten recommends a per-frame callback (`emscripten_request_animation_frame_loop` / `emscripten_set_main_loop`) over a blocking while-loop; Asyncify rewrites code to pause/resume at size and speed cost; JSPI uses VM promise integration with no size growth; `JSPI_EXPORTS` replaces deprecated `ASYNCIFY_EXPORTS` — [Emscripten Asyncify](https://emscripten.org/docs/porting/asyncify.html); [Emscripten runtime env](https://emscripten.org/docs/porting/emscripten-runtime-environment.html); [settings reference](https://emscripten.org/docs/tools_reference/settings_reference.html)
- Issue #22493 (Sept 2024) reports `emscripten_set_main_loop`/`request_animation_frame_loop`/`set_timeout` are incompatible with JSPI ("attempting to suspend without a WebAssembly.promising export") — [emscripten issue 22493](https://github.com/emscripten-core/emscripten/issues/22493)
- SoH web uses Asyncify for the game loop with an exclusion list; Asyncify instrumentation of randomizer table builders caused runaway allocation; one function grew to 53,185 locals making the Asyncify link take 2–3 hours until inlining was capped with `-sBINARYEN_EXTRA_PASSES=-ocimfs=1000` — [Shipwright PR 2](https://github.com/Project516/Shipwright/pull/2)
- Fallout Nevada's browser port uses Emscripten with Asyncify — [NMA thread](https://www.nma-fallout.com/threads/fallout-nevada-and-sonora-in-the-browser.222617/)
- Terraria's loop is driven from JS: `[JSExport] Init()` once, then `MainLoop()` per `requestAnimationFrame` — [velzie blog](https://velzie.rip/blog/celeste-wasm)
- Eaglercraft's WASM-GC build requires JSPI and (per an older README) would not run in Chrome without a flag or origin-trial token — [EaglercraftX README mirror](https://github.com/3kh0/eaglercraft-builds/blob/main/EaglercraftX_1.8_README.md)
- VCMI's demo pacing relied on SDL_Delay "which doesn't suit browsers" — [vcmi_wasm_demo](https://github.com/realkompot/vcmi_wasm_demo)

**Threads, SharedArrayBuffer, COOP/COEP**
- Emscripten pthreads need SharedArrayBuffer gated behind COOP/COEP; `-pthread` at compile and link; no single binary can both use threads and fall back; `PTHREAD_POOL_SIZE` pre-creates workers; `PROXY_TO_PTHREAD` runs `main()` off the browser thread; `Atomics.wait` does not work on the main thread so `pthread_join`/`usleep`/mutex locks busy-wait there; `ALLOW_MEMORY_GROWTH` with threads slows JS access to wasm memory; `-sMALLOC=mimalloc` reduces contention — [Emscripten pthreads](https://emscripten.org/docs/porting/pthreads.html)
- GitHub Pages cannot send COOP/COEP headers natively, so the Celeste/Terraria authors used a service-worker shim (coi-serviceworker / mini-coi) they would prefer to avoid; one user saw a white first load until manual reload — [HN 44101175](https://news.ycombinator.com/item?id=44101175)
- SoH web uses `coi-serviceworker.js`, reloads at most once per attempt, uses a fixed 8-worker pool, and cut the resource loader to 1–2 threads after a hang on a 16-thread machine — [Shipwright PR 2](https://github.com/Project516/Shipwright/pull/2)
- Generals-WebAssembly injects COOP/COEP client-side via service worker so hosting stays static — [Generals-WebAssembly](https://github.com/caiiiycuk/Generals-WebAssembly)
- Halo web requires WebAssembly threads and cross-origin isolation; the SHAR build requires `Atomics.waitAsync` — [halo-ce-universal](https://github.com/cybersecurity/halo-ce-universal); [Recompiled Games SHAR](https://recompiledgames.com/the-simpsons-hit-and-run-recompiled/)
- With .NET threads, all code runs in web workers and the canvas was only reachable from the DOM thread, so Terraria wrapped every FNA3D export with `emscripten_proxy_sync`; Celeste avoided this by moving to SDL3 + OffscreenCanvas (and patching Emscripten) — [velzie blog](https://velzie.rip/blog/celeste-wasm)

- FMOD replaced wholesale with Web Audio (GunZ) or, where it could not be recompiled (Celeste's proprietary FMOD failed inside a worker), its Emscripten `.o` files were extracted and relinked with generated wrapper code — [dev.to GunZ](https://dev.to/whiplash/how-i-fully-ported-a-heavily-windows-dependent-online-game-to-the-browser-with-webassembly-1fea); [velzie blog](https://velzie.rip/blog/celeste-wasm); OpenAL → WebAudio (Generals) — [Generals-WebAssembly](https://github.com/caiiiycuk/Generals-WebAssembly)

**Timing / frame pacing**
- Celeste Classic demo ran at double speed on 120 Hz displays because a fixed 60 Hz step was tied to requestAnimationFrame; browser timer jitter and millisecond rounding make variable timesteps hard — [HN 44101175](https://news.ycombinator.com/item?id=44101175); Eaglercraft's WASM build needs VSync or it runs "too fast" and chokes the event loop — [EaglercraftX README mirror](https://github.com/3kh0/eaglercraft-builds/blob/main/EaglercraftX_1.8_README.md); Perfect Dark web has issues above ~165 FPS — [perfect_dark_web](https://github.com/moeiscool/perfect_dark_web)

**Compile-time cost and toolchain fragility**
- SoH web: compile ~36 min, full job 53–55 min with a 2-hour CI timeout; `-O1+` on randomizer tables needed >4 GB RAM per file under exception handling; zlib/libpng sysroot paths hard-coded; `embuilder` runs every configure — [Shipwright PR 2](https://github.com/Project516/Shipwright/pull/2)
- Celeste's build instructions (dotnet workload, FNA, FMOD banks, Content) are described as "finicky"; "you may encounter issues on firefox" — [celeste-wasm README](https://github.com/MercuryWorkshop/celeste-wasm/blob/threads-v2/README.md)
- The hard part is "the details" — touch controls, multiplayer, save files, resolution/frame-rate — which take longer than the initial port (modeless, who ported Quake III and Cave Story) — [HN 44101175](https://news.ycombinator.com/item?id=44101175)

**WebGPU in Emscripten**
- Emscripten's built-in `-sUSE_WEBGPU` bindings are deprecated/unmaintained in favour of Dawn's `--use-port=emdawnwebgpu`, included since Emscripten 4.0.10; the transition is "not clean" and only core webgpu.h is considered stable — [Emscripten PR 24220](https://github.com/emscripten-core/emscripten/pull/24220); [Emscripten WebGPU docs](https://emscripten.org/docs/porting/multimedia_and_graphics/WebGPU-support.html); [pongasoft changelog](https://pongasoft.com/news/emscripten-ports.html)
- Safari 26 (Sept 2025) shipped WebGPU across Apple platforms — [Cinevva WebGPU vs WebGL](https://app.cinevva.com/guides/webgpu-vs-webgl-games)

### Inferences
- The ports that ship fastest (RTCW in ~1 h, OpenBW, WebTTD) start from codebases that already had an Emscripten branch or an SDL layer; the slow ones (SoH ~1 h CI per build, Celeste ~1 year) are those fighting threads + Asyncify + a managed runtime simultaneously.
- Asyncify remains the pragmatic default for legacy "blocking" game loops despite its cost; JSPI is not yet drop-in for Emscripten's main-loop APIs.
- Static hosting with a COI service worker + OPFS is now the de-facto distribution model for BYO-files ports; it removes backend cost and most legal exposure at once.

### Gaps
- No source quantified Asyncify's runtime overhead for a specific game port; only link-time and code-size effects were reported.
- No port documented using JSPI in production except Eaglercraft's WASM-GC client.
- Audio latency numbers were not reported by any port.

## Key Question 3: Managed-language (Java, C#) games — how were they handled?

### Takeaway
Java games go through TeaVM (Java bytecode → JS, now also an experimental WASM-GC target) as in Eaglercraft; C#/XNA-FNA games (Terraria, Celeste) use the official .NET `Microsoft.NET.Sdk.WebAssembly` (Mono-WASM) runtime with native FNA libraries linked as Emscripten `.a` archives, AOT compilation for playable speed, and .NET 9 threads — with heavy runtime patching to make MonoMod-style modding work.

### Cited Findings
- Eaglercraft compiles Minecraft's Java to JavaScript with TeaVM; its FAQ says DMCA-protected assets are not hosted and come from Mojang's official servers as with the official launcher — [TorrentFreak](https://torrentfreak.com/mojang-targets-repositories-of-browser-based-minecraft-copy-eaglercraft-230224/); [eaglercraft.com FAQ via TorrentFreak quote](https://torrentfreak.com/mojang-continues-crackdown-on-minecraft-pirates-230224/)
- EaglercraftX 1.8's WASM-GC runtime uses a custom TeaVM fork, is labelled experimental, requires JSPI, is incompatible with Safari, performs ~50% better (FPS/TPS) than the JS client, is built with `MakeWASMClientBundle` in `target_teavm_wasm_gc` producing a single `assets.epw` containing code and assets; `ramdiskMode` keeps worlds in RAM instead of IndexedDB — [EaglercraftX README mirror](https://github.com/3kh0/eaglercraft-builds/blob/main/EaglercraftX_1.8_README.md); eaglercraft.com also serves a 1.12.2-wasm client and a WASM-GC offline zip — [eaglercraft.com 1.12.2-wasm](https://eaglercraft.com/mc/1.12.2-wasm/); [downloads](https://eaglercraft.com/downloads)
- Eaglercraft architecture: OpenGL 1.3→WebGL 2 layer, EaglerXServer WebSocket→TCP proxy for real servers, worlds in IndexedDB, Web Audio — [mclist.io](https://mclist.io/knowledgebase/what-is-eaglercraft)
- Terraria: `Terraria.exe` decompiled with `ilspycmd` (ReLogic.dll had to be extracted from an embedded resource; .pdb symbols gave near-identical source), rebuilt on `Microsoft.NET.Sdk.WebAssembly` with Emscripten flags `-sMIN_WEBGL_VERSION=2 -sWASMFS` and `EmccEnvironment=web,worker`; native SDL3, FNA3D, mojoshader and FAudio linked as `.a` via `NativeFileReference`, produced by FNA-WASM-Build on GitHub Actions; full build ~8 min; .NET 8 crashed on thread creation so .NET 9 + `<WasmEnableThreads>true</WasmEnableThreads>`; AES missing in .NET WASM so OpenSSL was built with Emscripten and linked; before AOT ~2 FPS, after AOT fully playable including low-end devices — [velzie blog](https://velzie.rip/blog/celeste-wasm)
- Celeste: same engine; SDL3 gave OffscreenCanvas so no proxy layer; proprietary FMOD did not work in a worker so its Emscripten `.o` files were extracted and relinked; the WASM project is a stub loader that `Assembly.LoadFrom("/libsdl/Celeste.exe")` at runtime from the user's files, so no Celeste code is hosted; Everest is patched in-browser via MonoMod.Patcher with the DLL downloaded from GitHub — [velzie blog](https://velzie.rip/blog/celeste-wasm); [celeste-wasm how.md](https://github.com/MercuryWorkshop/celeste-wasm/blob/threads-v2/how.md)
- Modding on Mono-WASM: RuntimeDetour fails because Mono WASM is mostly interpreted (with a limited "jiterpreter") and wasm modules are read-only once instantiated; the fix rewrote IL in memory via Mono's `InterpMethod`/`mono_method_get_header_internal`, used `calli` with a magic token `0xF0F0F0F0` handled by a `transform.c` patch, used Mono hot-reload for tiny functions, and needed ~200 lines of Mono patches; 53 of 60+ Strawberry Jam mods worked; roughly a year of work — [velzie blog](https://velzie.rip/blog/celeste-wasm)
- The README notes AOT makes runtime reflection/detouring infeasible (so Everest was initially excluded) and that loading uses too much memory for mobile/low-end devices — [celeste-wasm README](https://github.com/MercuryWorkshop/celeste-wasm/blob/threads-v2/README.md); Webleste (celeste.r58playz.dev) is the near-complete port using .NET 9 threaded WASM and r58Playz's MonoMod WASM port; you must own the FNA version — [Webleste](https://celeste.r58playz.dev/)
- Hosting: terraria.mercurywork.shop (requires owning the game), celeste.r58playz.dev; repos MercuryWorkshop/terraria-wasm and celeste-wasm; Show HN May 29, 2025 (338 points) — [velzie blog](https://velzie.rip/blog/celeste-wasm); [HN 44101175](https://news.ycombinator.com/item?id=44101175)
- Engine-level managed paths: Unity's WebGPU graphics API is no longer experimental as of Unity 6000.6 with automatic fallback — [Unity discussions](https://discussions.unity.com/t/webgpu-out-of-experimental-in-unity-6-6/1734694); Godot 4.x web export supports only WebGL 2 (Compatibility renderer), WebGPU is a listed pending priority — [Godot docs](https://docs.godotengine.org/en/4.3/tutorials/export/exporting_for_web.html); [Godot priorities](https://godotengine.org/priorities/); Unreal has no official web target, Wonder Interactive's community UE5 WASM+WebGPU port runs Lyra in-browser — [Cinevva engines guide](https://app.cinevva.com/guides/web-game-engines-comparison)

### Inferences
- For C# games, the official dotnet-wasm toolchain plus FNA's prebuilt Emscripten natives is now a viable "copy this" path; the cost moves from graphics to runtime semantics (AOT vs interpreter, threads, crypto, reflection).
- Java has no first-party browser runtime, so TeaVM remains the only practical route; WASM-GC + JSPI is where its performance headroom is.

### Gaps
- No bundle-size, memory or FPS figures for Celeste/Terraria web beyond "100 MB+ wasm" and "2 FPS before AOT".
- No browser port of Stardew Valley, Hollow Knight or other MonoGame/Unity commercial titles was found in sources reached.

## Key Question 4: What do authors report about performance, load times and bundle sizes?

### Takeaway
Reported numbers are sparse and anecdotal: Web HL2 "100+ FPS" on a decent desktop, Perfect Dark web 60 FPS (experimental 240), PS2 recomp 60 fps at native res on a laptop iGPU, SoH ~45 fps software-rendered headless; data payloads range from ~90 MB (StarCraft) through 380 MB (RTCW), 400 MB (VCMI), 668 MB (Vice City) to ~2 GB (Generals), and managed-runtime wasm bundles exceed 100 MB.

### Cited Findings
- Web HL2: frame rates "can climb past 100 FPS on a decent desktop PC"; mobile may have problems — [Generation Amiga](https://www.generationamiga.com/2026/07/06/new-half-life-2-browser-port-includes-episode-one-and-episode-two/)
- Perfect Dark web: 60 FPS, experimental up to 240 FPS, issues above ~165; server ~1 core at 60 ticks/s — [perfect_dark_web](https://github.com/moeiscool/perfect_dark_web)
- PS2 recomp: 60 fps at native resolution on a laptop iGPU, GPU-bound at 2x; texture sampling ~1/3 of GPU time; VU1 and GS front-end each ~1/4 CPU on separate threads; ~1,000 small effect draws per frame batched in GoW II — [HN 50052251](https://news.ycombinator.com/item?id=50052251)
- SoH web: ~45 fps under software rendering in headless Chromium; ROM extraction ~4 min on a Raspberry Pi 5 first run, ~15 s in a later build; 33.5 MB oot.o2r; ~2.9 GB free memory on Pi after boot; compile ~36 min — [Shipwright PR 2](https://github.com/Project516/Shipwright/pull/2)
- Terraria: ~2 FPS interpreted, playable after AOT; build ~8 min; wasm files "100mb+" — [velzie blog](https://velzie.rip/blog/celeste-wasm); [HN 44101175](https://news.ycombinator.com/item?id=44101175)
- Eaglercraft WASM-GC ≈50% more FPS/TPS than JS — [EaglercraftX README mirror](https://github.com/3kh0/eaglercraft-builds/blob/main/EaglercraftX_1.8_README.md)
- Halo web "120 FPS" claim (LinkedIn post, secondary) — [LinkedIn](https://www.linkedin.com/posts/chrisheatherly_mitchell-hynes-has-decompiled-original-xbox-activity-7510765168692301824-gnN3)
- Data sizes: RTCW ~380 MB first load (pak0.pk3 316 MB) — [rtcw.pieter.com](https://rtcw.pieter.com/), [levels.io](https://levels.io/ported-return-to-castle-wolfenstein-to-web-with-ai); Vice City game.tar.gz ~668 MB compressed — [gta-vice-city-wasm](https://github.com/joncodeofficial/gta-vice-city-wasm); Generals ~2 GB payload decompressed with ~130 MB peak RAM — [Generals-WebAssembly](https://github.com/caiiiycuk/Generals-WebAssembly); VCMI ~400 MB pack — [vcmi_wasm_demo](https://github.com/realkompot/vcmi_wasm_demo); StarCraft ~90 MB — [playscbw](https://playscbw.com/?locale=en); GunZ SFX 44.3 MB → 5.3 MB via Opus, startup <10 s — [dev.to GunZ](https://dev.to/whiplash/how-i-fully-ported-a-heavily-windows-dependent-online-game-to-the-browser-with-webassembly-1fea)
- Memory64 costs performance ("potentially large performance hit depending on workload") — [SpiderMonkey blog](https://spidermonkey.dev/blog/2025/01/15/is-memory64-actually-worth-using.html)

### Inferences
- Nobody publishes native-vs-wasm benchmarks; authors report "playable" thresholds. Where GPU work dominates (PS2 GS, HD art), WebGPU compute is what makes 60 fps possible; CPU-bound legacy engines are comfortably fast under wasm32.
- Payload size, not CPU, is the practical UX limiter, which is why OPFS caching, Brotli segmentation and streaming-on-demand recur in every 2026 port.

### Gaps
- No published load-time measurements for any of the big ports; no wasm binary size for SoH, HL2, Halo or Generals.

## Key Question 5: Which tools, templates and boilerplates get reused?

### Takeaway
Reused building blocks are: Emscripten's SDL2/SDL3 ports and `emcmake`; GL4ES and LostMyCode/d3d9-webgl (and its d3d8 derivatives) as graphics shims; libultraship/fast3d for N64 decomps; FNA-WASM-Build + `Microsoft.NET.Sdk.WebAssembly` for C#; TeaVM for Java; coi-serviceworker/mini-coi for isolation on static hosts; OPFS + service-worker and IDBFS patterns for data; WebSocket-to-UDP gateways and WebRTC meshes (MQTT or copy-paste signaling) for multiplayer; Wisp for TCP tunnelling; emdawnwebgpu for WebGPU; and the recompiledgames/awesome-decomp-games indexes to find prior art.

### Cited Findings
- ioquake3's in-tree Emscripten build (emcmake + client-config.json + static HTTP) is the canonical id Tech 3 template; q3js, Urban Terror and Jedi Academy (OpenJK) web builds descend from it — [ioquake/ioq3](https://github.com/ioquake/ioq3); [lklacar/q3js](https://github.com/lklacar/q3js); [Recompiled Games](https://recompiledgames.com/)
- Wwasm's SP Emscripten patch set was transplanted into iortcw MP; GL4ES for GL1.x→WebGL2 — [levels.io](https://levels.io/ported-return-to-castle-wolfenstein-to-web-with-ai)
- LostMyCode/d3d9-webgl (from the GunZ port) is the base of Generals' `d3d8webgl` — [dev.to GunZ](https://dev.to/whiplash/how-i-fully-ported-a-heavily-windows-dependent-online-game-to-the-browser-with-webassembly-1fea); [Generals-WebAssembly](https://github.com/caiiiycuk/Generals-WebAssembly)
- libultraship fast3d renderer reused by SoH web and Perfect Dark web — [perfect_dark_web](https://github.com/moeiscool/perfect_dark_web); [Shipwright PR 2](https://github.com/Project516/Shipwright/pull/2)
- FNA-WASM-Build produces SDL3/FNA3D/mojoshader/FAudio `.a` archives via GitHub Actions; the FNA.WASM.Sample guide and dotnet wasmbrowser template were the starting point — [celeste-wasm README](https://github.com/MercuryWorkshop/celeste-wasm/blob/threads-v2/README.md); [velzie blog](https://velzie.rip/blog/celeste-wasm)

- TeaVM (custom fork for WASM-GC) for Java — [EaglercraftX README mirror](https://github.com/3kh0/eaglercraft-builds/blob/main/EaglercraftX_1.8_README.md); WASI SDK used for OpenBW's engine — [danglade/openbw](https://github.com/danglade/openbw)

### Inferences
- There is no single "wasm-game starter kit" in use; instead porters copy the nearest sibling port (RTCW from Wwasm, Generals from Lolendor's fork, Perfect Dark from SoH's renderer, Terraria from FNA.WASM.Sample).
- The graphics shim choice is dictated by the original API: GL1.x → GL4ES; GLES2-ish → Emscripten's GL emulation; D3D8/D3D9 → d3d9-webgl family; modern → native WebGPU via emdawnwebgpu/wgpu.

### Gaps
- No documentation of Dvijoke d8web beyond its name in a README; no public source for the GunZ "wrap" script or the Celeste FMOD wrap script.

## Key Question 6: Which ports were taken down for legal reasons?

### Takeaway
Takedowns cluster where assets or trademarks are distributed: Take-Two vs DOS.Zone's Vice City (Dec 2025), Activision vs the Black Ops 2/Kino browser clones (Oct 2026), Mojang vs Eaglercraft (2023, 92 GitHub repos + Discord/GitLab), Nintendo vs an SM64 browser clone and the SM64 PC port; BYO-files projects on GitHub have largely survived.

### Cited Findings
- DOS.Zone's Vice City browser port (Dec 2025) was removed after a DMCA from Take-Two's agent Ebrand; the notice objected even to inviting users to input data/keys from their original copies; Quenq later relaunched the code — [XDA](https://www.xda-developers.com/gta-vice-city-now-playable-in-a-browser-dos-zone/); [Tom's Hardware](https://www.tomshardware.com/video-games/browser-run-copy-of-grand-theft-auto-gets-taken-down-by-dcma-take-two-says-dos-zone-infringed-companys-intellectual-property-rights-despite-disclaimers-and-requirement-to-own-original-copy-of-title-to-run-full-game-online); [Outlook India](https://respawn.outlookindia.com/gaming/gaming-news/gta-vice-city-is-now-playable-in-browsers)

### Inferences

### Gaps
